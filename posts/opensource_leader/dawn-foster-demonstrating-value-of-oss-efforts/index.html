让开源工作的价值被看见：Dawn Foster 关于「证明价值」的战略方法

开源团队最常见的困境不是做不好工作，而是说不清工作的价值。Dawn Foster 在 Open Source Summit 的演讲给出了一个反直觉的起点：不要从指标开始，从组织目标开始。本文整理自她的演讲《Strategic Approach To Demonstrating the Value of OSS Efforts》，内容涵盖目标对齐、关键性判定、项目健康风险与价值沟通四个层次，也收录了现场问答中关于「我们不写软件，如何证明价值」的那个难题。

开场：一个几乎人人都遇到过的难题#

（配图由大模型 sensenova-u1.5-lite 与 skill sn-image-base 生成，象征「把无形的投入放到天平上称一称」。）

任何在组织内部从事开源工作的人——无论身处开源项目办公室（OSPO）、其他团队，还是在企业、学术机构、非政府组织或公共部门——大概都经历过同一个困境：如何展示和证明这项工作的价值。

Dawn Foster 在过去 25 年多的时间里，一直在帮助企业战略性地思考如何使用和贡献开源软件。其中很大一部分工作，就是利用数据和指标去证明开源项目的价值。她曾在 Intel 和 VMware 任职，也作为志愿者在 CNCF（云原生计算基金会）贡献，担任过贡献者战略技术咨询小组的联合主席，并参与治理工作组。多年来她至少与上百个开源项目打过交道。

但她给出的第一个提醒，就与「指标崇拜」相反：

我深度参与了 CHAOSS（社区健康分析开源软件）项目，但我不喜欢孤立地思考指标。我更愿意做战略层面的思考：如何利用从指标中学到的东西，去改进我们的开源工作。这也是为什么这场演讲的核心不在指标本身，而在于我们如何把指标作为「展示开源工作价值」的一部分。

由于她的经验主要在企业环境中，演讲以此为主要背景，同时也谈到大学、公共部门等场景下价值证明的差异。

一、战略与目标对齐（Goal Alignment）#

展示开源工作的组织价值，第一步是目标的一致性——把你的开源工作与组织更广泛的目标对齐。在此基础上，还要通过审视项目的关键性（criticality）与健康度（project health）来排定优先级，最后才是用能引起领导团队、出资人和利益相关者共鸣的方式把价值讲出来。

CHAOSS 的从业者指南#

CHAOSS 常被误认为只是「一堆工具和指标」。事实上它近年开发了「从业者指南」系列（Practitioner Guide Series）。每份指南聚焦一个主题，其价值不在指标，而在于如何跨越关键领域，在开源工作中做出真正有意义的事。目前涵盖改善贡献者可持续性、组织参与度、响应速度、评估可行性、研究软件影响力等方向。

其中一份专门讲「在组织内部展示开源努力的价值」——正是这场演讲的核心。大多数指南被设计成「入门指南」，帮助人在某个主题上快速取得进展；而「证明价值」对许多 OSPO 和开源团队来说是真正的硬骨头：你得向领导、出资人和利益相关者证明这件事值得长期投入。

两种常见但无效的说法#

开源团队往往默认把工作描述成「对开源的贡献」。Dawn 指出，这种说法听起来很像慈善事业——「这是为了社区的利益」。这当然是事实，但它极难引起利益相关者的共鸣。

另一种常见做法是提供工作量概览：贡献数量、维护者数量、代码提交量。这只能说明人们投入了时间和精力，却依然没有证明这些时间带来了什么回报（return）。

从组织的角度来看，无论你在哪类组织工作，展示开源工作价值的最好方法是：证明这项工作如何帮助你的组织实现其目标。

组织的领导层必须放眼全局，优先考虑对整个组织影响最大的工作。这意味着：如果你希望领导层继续为 OSPO 或其他开源工作提供人员和经费，你需要证明的不是「我们很努力」，而是「我们的工作为什么与组织内其他争夺有限资源的努力相比同等重要，甚至更重要」。

拥有清晰的开源策略，能够讲清开源工作如何帮助实现组织目标，是让领导层理解这件事的最好途径。

企业案例：Pivotal 与 Kubernetes#

Dawn 在 Pivotal 担任开源战略师期间，Kubernetes 是其产品战略的重要组成部分（这是在 VMware 收购 Pivotal 之前）。当时公司正处在把主要产品底座从 Cloud Foundry 迁移到 Kubernetes 的过渡期——那是 2018–2019 年前后，Kubernetes 远不如今天成熟。

这是一次巨大的转变：Pivotal 是 Cloud Foundry 的创建者之一，在那个项目里拥有巨大影响力；但对 Kubernetes，他们才刚刚起步。

她做了几件事：花大量时间与推动这次转变的 CTO 交谈，与负责各产品策略的负责人沟通，搞清楚未来几年要达到的目标；同时开始参与 Kubernetes 社区，与自家工程师讨论各个领域的优劣。把「未来几年我们需要什么」与「Kubernetes 里需要改进什么」对上。

然后她把这些信息写成了一份很长但清晰的书面策略，把公司的开源 Kubernetes 工作与整体使命、目标和产品战略联系起来。通过展示长期产品战略如何依赖 Kubernetes 代码库的特定领域、并概述需要在哪里贡献才能支撑这些产品，她成功地为上游项目争取到了人员分配。此后团队持续跟踪这些贡献，用数据向公司证明自己提供的价值。

其他环境：大学、公共部门与外部出资人#

在大学、学术界或公共部门，情况会更复杂一层：某些场景下你还需要向外部出资人证明价值。例如 Sloan 基金会资助了许多大学的 OSPO 和其他工作。

这时你不仅要向已经出钱的人证明价值，还要向未来的出资人证明。逻辑与企业环境类似：你需要了解特定出资人的目标，确保提议的工作与其目标一致、符合他们的拨款策略或公开征集要求。这通常是在组织内部证明价值之外的额外工作。

除组织领导与出资人之外，还需要与其他利益相关者的目标、法规或指令保持一致，这在公共部门或非营利 OSPO 中尤为重要。例如，欧盟及其他国家正在推动「数字主权（digital sovereignty）」——欧盟把开源视为在其数字领域行使战略独立性的关键部分。这可以帮助组织为某些开源倡议提供理由，把工作价值表述为更广泛的数字主权努力的一部分。

同样，政府指令与法规也会影响企业环境中的开源项目与供应链。例如软件物料清单（SBOM）的相关指令，以及欧盟《网络弹性法案》（Cyber Resilience Act）。遵守法规与指令本身，也是展示工作价值的一部分。

二、关键性与优先级排序（Criticality and Prioritization）#

CHAOSS 的价值展示指南提供了一个框架：通过结合项目关键性（criticality） 与项目健康风险（project health risk），帮助排定开源工作的优先级。

第一步是确定关键性——它定义了项目对你组织的重要程度。关键项目可以用来构建 OSPO 战略，以领导层能理解的方式展现开源工作的重要性。

一个必要的澄清：这里的「关键性」是针对特定组织的，与 OpenSSF 的关键性评分不同——后者定义的是项目对整个生态系统的影响力和重要性。

很多人经常混淆「被频繁使用的项目」（规模问题）与「真正具有战略意义的项目」。我判断的方法是：我是否可以轻松替换它？

  • 如果你用的是一个小型代码库，很容易用其他库替换或自己重写，那它不太可能是关键项目。
  • 另一方面，像 Kubernetes 或 Linux 内核这样极其复杂的软件，无法轻易被替换；如果你依赖它执行重要活动或产品，那它就是你的关键项目。

在 VMware，她的团队负责维护「战略项目清单」。高管们经常问「哪些开源项目最重要」，而合规团队会提交一份在自家产品中出现频率最高的软件包清单——但那通常都是些小工具，并不是高管真正关心的战略级项目。

他们把这个问题换了个问法，去问各业务部门的产品人员：「离开哪些开源项目，你们就无法交付产品？」 这份清单不仅为高管提供了一个窗口，还帮助业务部门在参与同一个项目时进行协调，并为分配人员去贡献提供了理由。

在大学与学术环境中，关键性的概念依然适用，只是方式略有不同。例如可以关注「研究软件的影响力（research software impact）」，以此理解开源软件在实现教育成果方面的重要性。在公共部门，如果开源工作影响了基础设施、网站或用于向公众提供关键服务的应用，那么它的价值就可以被证明。

三、项目健康风险管理（Project Health Risk）#

确定关键性之后，就要考虑项目健康风险。有些开源项目比其他项目更健康、更可持续。一个对你组织很关键且很健康的项目，优先级可能低于一个同样关键、但充满风险、需要你组织帮助才能变健康的项目。通过分配资源改善项目健康状况，你降低的是使用它的风险。

Dawn 经常把项目健康风险框架化为「可行性（viability）」问题——这是管理风险、减少潜在中断几率的良好起点。CHAOSS 有一份基于 Gary White（Verizon）工作的从业者指南，提供了框架与指标，帮助全面审视项目的治理、社区、合规性与安全性。

思考项目健康风险时，不仅是识别风险，还要思考你如何改善该项目的健康状况——这本身就是证明工作合理性的一部分。

可以分配员工时间去改善贡献者可持续性、组织参与的多样性等，特别是对那些对组织极其关键的项目。

组织投资的优先级 = 关键性 + 项目健康风险。

这在每个组织都是独一无二的。需要把有限的资源明智地用于最高优先级的领域。

四、沟通价值（Communicating Value）#

确定了关键项目并完成优先级排序后，还需要向领导层沟通：你的工作如何帮助组织实现目标。

太多时候，OSPO 倾向于测量「容易计算的东西」（比如 commit 数量），而不是「真正有价值的活动」。

与领导、出资人和其他利益相关者的沟通，必须精准聚焦于工作的价值。例如可以沟通：你需要的特定功能是否完整且稳定？你关心的问题是否得到解决？你依赖的项目是否健康可持续？

这通常归结为一句话：衡量重要的事情，并用数据讲述工作价值的故事。

四个维度：衡量 OSPO 价值#

Linux 基金会的 Ibrahim Haddad 博士最近撰写了一份报告，提出衡量 OSPO 价值的四个相互关联的维度：

  1. 成本规避（Cost Avoidance）：OSPO 通常不产生直接收入，但可以减少重复劳动、提高效率、降低维护成本，实现财务合理化。
  2. 韧性（Resilience）：通过主动衡量，避免引发高调的危机。
  3. 风险预见（Risk Foresight）：尽早发现潜在问题，以减轻影响、避免事故。
  4. 战略影响力（Strategic Influence）：OSPO 如何通过在开源生态系统中的存在、参与和影响力进行战略投资——这对组织的现在和未来都至关重要。

问答环节（Q&A 摘要）#

Q1：我们的产品不是软件，管理层认为开发软件是供应商的事，如何证明开源工作的价值？

这确实更难。但即使你们不开发软件，软件也是你们向客户提供服务不可或缺的一部分。必须设法把开源底层技术与组织的整体业务目标（交付服务、提升效率等）联系起来。

Q2：对于想要开始使用和贡献开源软件的公司，如何说服管理层？

强调「不要重复造轮子」。现有的开源软件已经很成熟、可靠且安全。与其浪费大量工程时间在内部重新开发，不如利用已经存在的技术。同时可以引用大型银行（如 FinOS 领域）和政府部门都在安全使用开源软件的例子来提供背书。

结语：把「做了什么」翻译成「换回了什么」#

这场演讲最有价值的地方，是它把 OSPO 的日常焦虑换了一个问法。开源团队习惯自证清白——我们提交了多少、维护了多少、响应了多快。但领导层从来不缺这类数字，他们缺的是判断：这些投入，换回了什么，换回了多少，以及不继续投会发生什么。

Dawn 给出的路径并不神秘：先对齐目标，再用「能否被替换」来判定关键性，用健康风险来排优先级，最后用利益相关者听得懂的语言讲出兑现的价值。四个步骤里没有一步是技术性的——它们全都是制度性的，也正是 OSPO 这个角色真正的专业所在。
