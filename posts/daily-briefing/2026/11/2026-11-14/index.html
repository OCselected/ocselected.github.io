「开源之道」 2026-11-14 搜集事件和材料#

今天三条线索指向同一个动作：「读得来的公开」和「能被检验的公开」不是同一件事。

① 先看公开是不是可审。 欧盟 DSA 要求超大型平台披露推荐系统信息，X 也确实主动开源了推荐流水线。但一篇代码级审计从用户可见的时间线开始反向遍历，把每个组件追溯到上游生产者，检查它是否真的在 serving 路径上可达——结果找出 13 处透明度死路：公开代码依赖、但释出内容里没有的模型、服务、标签列表与配置值。决定「哪些帖子被过滤、如何排序」的组件，全部落在可检视性最低的层级。 法规写的是「披露」，审计需要的是「可达」——这两者在代码层面差着 13 个断点。

② 再看判据能不能写出来。 一篇把「维护者明确标记为 slop 的 PR」做成项目层级实证：这类 PR 自 2025 年中上升、2026 年 5 月见顶；以「加东西」为主、极少被合并、通常 3 天内关闭；作者主动披露用过 AI 的仅 14%，只有 1% 是在被要求之后才披露；绝大多数关闭或标记时不给任何理由——理由谱系从「构建失败」一直延伸到「看起来就像 AI 写的」。这不是维护者懈怠，是评审成本的第二次转移。

③ 最后看治理能不能被度量。 Git2KG 从 Git log 抽共同编辑与代码归属、与 issue 追踪器的沟通网络对齐、按时间窗切片，把「谁的文件在什么时候变成了谁的文件」变成一条可追溯的曲线。它分别建模两种社会关系——协作与产权——再让它们在同一张图上对话，这正是公地治理的现实形状：协作的人未必是持有的人。

新闻面，Linux 基金会 OpenSSF 的 308 人调查里，「预期答案」（93% 担心供应链攻击）如期出现，但最要紧的是最不戏剧化的一组：83% 担心高更新量带来的维护负担，只有 44% 觉得自己准备好了；60% 的组织表示 AI 编码工具增加了外部依赖，而团队只有约一半时间会审查传递依赖。Project Pulse 深看 Apache Kafka：抽查 30 个已合并 PR，自合自审 0 个；trunk 六天 56 个提交、32 位作者，最高频者仅占 26.8%。

📄 论文三条#

1. 开源的推荐算法里，有 13 处走不通的死路：当「公开代码」不等于「可被审计」#

A Code-Level Audit of X · Luka Bekavac、Simon Mayer（arXiv:2611.16800，cs.CY / cs.SE，2026-11-12）

链接：arXiv:2611.16800｜DOI 10.48550/arXiv.2611.16800

摘要：欧盟《数字服务法》（DSA）要求超大型在线平台披露推荐系统的信息，并向经审核的研究者开放非公开数据——可能延伸到推荐算法代码本身。但没人知道这种代码释出在多大程度上能支撑实质性的第三方审计。作者提出一套代码级审计方法：对仓库做反向遍历（backwards-walk traversal），从用户可见的时间线开始，把每一个对决策有影响的组件追溯到它的上游生产者，检查它是否真的在 serving 路径上可达，并按四级可检视性方案给每个组件定级。把这个流程套到 X 主动开源的推荐流水线上，他们找出 13 处透明度死路：公开代码依赖、但释出内容里没有的模型、服务、标签列表与配置值。决定「哪些帖子被过滤、如何排序」的组件，全部落在两级可检视性最低的层级，而这个模式在 2025 年把专有 Grok 模型嵌入审核、标注与排序之后进一步加剧。反向可达性检查还揭示出第二类问题：释出仓库里保留着 2025 年流水线已不再触达的 2023 年代码，共 36 处参数引用——不做可达性检查的话，它们看起来就像死路。文末讨论了真正可审计还需要哪些额外制品。

为什么与「开源之道」相关：这篇论文做了一件「开源之道」一直在做的事——把「开放」这个动词拆成可检验的判据。X 的做法在名义上符合「代码公开」，但公开的仓库如果缺了决定输出的那几个闭环环节，它给出的就不是可审计性，而是一种外观。这与 11-01 简报里那道题同源（「机器审核机器」里三个 AI 审阅者全都放过）：审阅这个动作本身不产生信任，能独立复现的判据才产生信任。文章对 DSA 的隐含批评也值得记下：法规写的是「披露」，审计需要的是「可达」。这两者在代码层面差着 13 个断点。

「开源之道」点评：最有价值的不是那 13 条死路，而是方法论可以平移。「这件事真的是开源的吗」这个问题，长期靠立场和宣言来回答；反向可达性遍历提供了一个新的回答方式——从最终产出往回走，看每一环是否真的接得上。大分流 2.0 里那些「特许工程代码」「局域网共享」「赛博庄园」，缺的正是这一遍反向走。补一句克制的话：X 至少还主动释出了代码，让它能被这样审——可审计性的最低门槛是有人愿意被审，X 迈过了这道门，只是没走完。

2. 「AI slop PR」第一次被做成项目层级的实证：86% 不披露，多数无理由关闭#

An Empirical Study of Maintainer-Identified AI Slop Pull Requests in Free and Open Source Software Projects · Hugo Raskin、Xavier Devroey、Benoît Vanderose（arXiv:2611.15159，cs.SE，2026-11-11）

链接：arXiv:2611.15159｜DOI 10.48550/arXiv.2611.15159

摘要：生成式 AI 把向 FOSS 贡献的门槛降到了史上最低，随之出现「AI slop PR」——低质量、低价值的生成式 PR。此前的研究从理论、平台层或从业者自述角度切入，没有项目层级的实证。本文专门盯一类样本：被维护者明确标记为 slop 的 PR。用混合方法，作者追踪这批 PR 的来源、量化其体量、描述其特征，并梳理维护者标记或关闭它们的理由。结果：维护者认定的 AI slop PR 体量自 2025 年中开始上升，2026 年 5 月达到峰值；这类 PR 以「加东西」为主（additive），极少被合并，通常在 3 天内被关闭；作者主动披露使用了 AI 的仅 14%，其中只有 1% 是在维护者要求之后才披露；绝大多数 slop PR 被关闭或标记时，维护者没有给出任何理由。开放编码出来的理由谱系很宽——从具体的东西（构建失败）到意识形态式的或纯粹直觉式的（「看起来就像 AI 写的」）。作者自陈这是对一个早期阶段现象的探索性研究，并指出 GenAI 对维护者的压力，以及开源开发实践需要转向。

为什么与「开源之道」相关：这份实证把 11-13 简报里那道题（「可合并性是一套规则」）翻到了背面。上一期问的是判据能不能被写出来；这一期回答的是当判据写不出来时，实际发生了什么——维护者用直觉（「looks AI to me」）行使否决权，而且不解释。这不是维护者懈怠，是评审成本的第二次转移：AI 把产出的边际成本压到零，评审的边际成本就变成新的稀缺要素，而稀缺要素的持有者会把配额用在最省力的判据上。3 天内关闭、少给理由，正是配额保护的行为特征。

同时，14% / 1% 这两个披露率是这篇里最硬的一条制度事实：AI 使用披露依赖自愿，而自愿披露的覆盖率是 14%。任何以「要求披露 AI 使用」为前提的治理设计（从期刊到 PR 模板），都应当先看一眼这个数字。

「开源之道」点评：奥斯特罗姆讲公地治理需要低成本冲突解决机制；slop PR 说的正是这个机制的成本失衡——关闭一个 PR 几乎零成本且不需理由，重建一次信任却要维护者付出他最不愿意付的东西（时间与解释）。这里也不该把矛头指向「用 AI 的人」：问题不在工具，在于准入制度仍假设「提交成本高」这个前提依然成立。当提交成本塌陷而准入规则不变，筛选负担必然全部落到守门人身上——这是制度滞后，不是道德问题。

3. 把「谁和谁一起改了什么」做成时间序列：给公地治理补一台测量仪#

Git2KG: Mining socio-technical relationships in GitHub repositories as temporal knowledge graphs · Lennart Hessenauer、Lisi Qarkaxhija、Ingo Scholtes（arXiv:2611.15509，cs.SE，2026-11-11）

链接：arXiv:2611.15509｜DOI 10.48550/arXiv.2611.15509

摘要：Git 与 GitHub 的普及让协作开发留下了大量数据，但现有挖掘方法通常分开处理两类关系：issue 追踪器里的开发者沟通网络，与编辑历史里的开发者—开发者共同作者网络、开发者—文件代码归属网络。要把它们整合进同一张知识图谱，需要解决作者身份消歧与多源实体匹配，而多数网络分析又采用时间聚合视角，把协作的时间动态抹掉了。Git2KG 是一个可扩展的 Python 库，从 GitHub 仓库挖掘时间知识图谱：从 Git log 中提取细粒度的共同编辑关系与代码归属，消歧开发者身份后与 issue 追踪器中提取的管理网络、沟通网络对齐；按固定大小、不重叠的时间窗切片，得到每个仓库的一系列图谱快照；支持计算下游机器学习所需的节点特征与标签，并可导出到 PyTorch Geometric、PathPyG、NetworkX 做时序网络分析、可视化与图学习。

为什么与「开源之道」相关：这篇是工具论文，但它补的是「开源之道」长期缺的一样东西：对「治理」这一层的可测量性。威廉姆森 L3（治理机制）之所以难以实证，一个很实际的原因是——代码归属会随时间在人与人之间漂移，而这种漂移过去只能在某个时间点拍快照。时间知识图谱把「谁的文件在什么时候变成了谁的文件」变成一条可追溯的曲线，这恰恰是判断「项目还在不在同一个社区手里」所需要的那种证据。

顺带一提它在方法论上的自律：作者把身份消歧（author disambiguation）明确列为难点并作为独立步骤处理。这一点很重要——任何关于贡献分布的实证，如果身份对齐不准，结论就不可信。11-13 那篇「19.3% 的提交带 AI 署名」的研究同样依赖这一环。

「开源之道」点评：工具不产生判断，但没有工具的判断只能是印象。这篇文章值得读的地方，是它把「共同编辑」和「代码归属」当成两种不同的社会关系（协作与产权）分别建模，再让它们在同一张图上对话——这正是公地治理的现实形状：协作的人未必是持有的人。 对做项目健康度评估的人，这是比任何单一指标更接近制度现实的底图。

1. 报告写的是「AI 供应链攻击」，数据指出的却是最无聊的那件事：组件更新跟不上#

来源：Linux Foundation / OpenSSF（2026-11-10，原发于 OpenSSF 博客 11-09，作者 Abby Kearns）——OpenSSF 博客

摘要：《State of AI Impact on Software Security and Cybersecurity 2026》今年夏天调查了 308 位在企业与开源项目中做安全工作的人，由 OpenSSF、LF AI & Data 与 ActiveState 赞助。报告的「预期答案」确实出现了：93% 担心供应链攻击、90% 担心提示注入。但作者指出最要紧的发现是最不戏剧化的那一组：83% 担心高更新量带来的额外维护负担，只有 44% 觉得自己准备好了，而 43% 已经在处理这个问题；60% 的组织/项目表示 AI 编码工具增加了外部依赖数量（只有 16% 说减少）；团队只有大约一半的时间会去审查传递依赖；58% 说自己的发版速度快过安全评审的跟进速度。修复被推迟的原因，头两位是担心改坏东西（28%）与没时间（22%）。没有专职 AI 威胁安全团队或角色的团队中，只有 23% 能修掉大部分问题。

「开源之道」点评：这条和今天那篇 AI slop 论文是同一枚硬币的两面——AI 压低了「增加」的成本，却把「维护」的成本留在了原地。报告里 83% 对 44% 的落差，测的不是安全意识，是维护这项劳动的定价：新增依赖是决策者在会上做的，跟进更新是某个人在周五下午做的，两者从来不在同一张预算表上。

2. KubeCon EU 2026：AWS 升为 Linux Foundation 白金会员#

来源：Computer Weekly / Linux Foundation（2026-11-12）

摘要：在 KubeCon + CloudNativeCon 上，AWS 成为 Linux Foundation 白金会员。这距 AWS 2019 年因 Elasticsearch 许可证争端 fork 出 OpenSearch、与 LF 关系一度紧张，已过去七年；LF 官方公告此前在 10 月已发布，媒体在大会期间做了跟进报道。

「开源之道」点评：白金会费不改变项目，改变的是企业可以选择走开的成本。 2019 年那次 fork 是「退出」选项的一次真实演示；2026 年的白金会员是「发声」选项的重新定价。制度经济学对这类变化的解读很直接——重要的不是会员名单，是退出威胁的可信度：当一家公司的替代路径（自建 OpenSearch）已经被证明可行且成本可承受，它的忠诚就不是制度约束的结果，而是成本核算的结果。这条只记录，不做延伸判断。

🔍 Project Pulse：Apache Kafka —— 一个把「不该做的事」变成默认值的项目#

仓库：github.com/apache/kafka｜Apache-2.0｜默认分支 trunk｜18,679 commits｜2026-11-08 → 11-13 窗口实测

选择理由：11-11 简报已看过一次 Kafka 的 AI 署名数据；今天换个角度，看它在合并侧的行为——这是 11-13 两个项目被指出的同一个问题（自合自审）的反面样本。证据全部来自 GitHub API 与仓库根目录文件，不是新闻稿。

【L1 · 发布节奏】 ASF 的 Kafka 仓库不走 GitHub Releases（tags 端点取回的仍是 0.7.x 孵化期候选标签），版本发布走 ASF 的邮件列表 + release/ 目录与 doap_Kafka.rdf 流程。11-08 → 11-13 六个自然日窗口内：trunk 上 56 个提交、32 位不同作者，最高频的 David Jacot 也只有 15 个（26.8%），前五名合计约 46%。这是一条长尾极长、头部不集中的分布——没有任何一个人占到「他一停项目就停」的量级。

【L2 · 治理结构 —— 今日主信号】 抽查 11-08 → 11-13 窗口内更新的 44 个已合并 PR，对前 30 个逐个读取 user.login 与 merged_by：

自合自审：0 / 30。

也就是说，这个项目在合并这一环上没有任何一个样本是作者给自己盖章。样本中既有 ASF committer（dajac、mjsax、lianetm、smjn、fvaleri 等），也有明显的组织外账号（suzhiking、40436michael、unknowntpo、Russole、gabriellefu、chungyichi），后者全部由他人合并。这与 11-13 简报里 OpenShell（12 个样本 11 个自合）与 Agent Skills（捐赠章程由 Lead 自己写、自己合）形成了直接对照。
