「开源之道」 2026-11-12 搜集事件和材料#

今天三条线索收束于同一个动作：当资源生产的成本塌到零，制度就必须把「谁能代表谁」从工作量证明改成身份证明。

① 先看组织内部。 影子 IT 是一桩老问题，但 agent 让它长得更快——造工具的成本近乎归零，agent 以用户本人权限行事，它留下的脚本、自动化与 MCP server 本身又是未经批准的新资产。论文给出了一个可以抄下来的条件：一旦产出物的繁殖速度快于组织的退役速度，影子 IT 就指数增长。而退役的第一步是检测，检测的前提是可归属。

② 再看公地内部。 开源话语里，代码复用几乎总是被当作优点讲；今天这篇给了红利账户的另一栏——复用同时是一条不问许可、不问上下文的传染通道。当漏洞的传播路径不是依赖图而是复制粘贴，SBOM 这套基础设施在结构上是盲的。

③ 最后看身份层。 Linux Foundation 正式接下 Agent Name Service：不另造一套信任根，而是接 DNS 与 X.509；五个 TSC 席位里三个来自 GoDaddy，而章程第 2.d 条把这件事写进了过渡期。今天最有价值的一点是——这套制度第一次可以被逐字检查。

Project Pulse 逐条读了它：15KB 章程、765 行 GOVERNANCE.md、8,050 字节的失败模式对照表、Peribolos 名册。这是 2026 年至今最值得保存的一份「公司项目转基金会」标本。

📄 论文两条#

1. 影子 IT 的复利：当 agent 造工具近乎免费，组织追缴的速度必须超过它繁殖的速度#

Detecting Shadow AI: Unsanctioned LLM Agents on Enterprise Endpoints: A Taxonomy, an Open Detector and a Controlled Evaluation · Jeremy Canale、Fabien Soulis（arXiv:2611.12377，cs.AI / cs.CR，2026-11-09）

链接：arXiv:2611.12377｜DOI 10.48550/arXiv.2611.12377

摘要：影子 IT——IT 部门未批准的技术使用——是一桩由来已久的治理难题。作者论证自主 AI agent 会让它长得更快：agent 让造工具的成本近乎归零，agent 以用户本人的权限行事，而它留下的脚本、自动化与 MCP server 本身又是未经批准的新资产。文章先给一个简单的复利模型：一旦 agentic 产出物的繁殖速度快于组织的退役速度，影子 IT 就指数增长，而退役的第一步是检测。随后是实测部分：作者提出九类 agent、六层端点足迹的分类法，并指出只靠进程与连接结构的规则无法把 agent 与它的「行为孪生体」（同一个程序但连的是非 AI 服务）分开。他们发布 Agent Detector（开源 Windows 检测器），把行为锚定到远程服务的身份上，再与配置、安装、执行历史关联，用 39 个工具 / 184 条 LLM 端点条目的目录；它通过一条必须确认的通知告知用户，而不是阻断。在 12 个合成 agent、3 个 AI 组件、9 个良性负载的受控测试台上重复 5 次：两条纯行为规则把每一个行为孪生体都误报，Agent Detector 一个没误报，并在多数轮次中检出全部 agent。它的局限是时间性的：对藏在共享 CDN 背后的厂商连接，只有在 DNS 缓存还持有厂商名字的那一到五分钟内才可归因；间歇性 agent 大约每三次扫描才被看到一次。单次扫描约 154 ms。作者自陈测试台太小，不足以给检测器排位——它测绘的是每一类证据各自能看见什么。

为什么与「开源之道」相关：这是第一篇把「AI 让生产成本趋零」这句口号换算成一个可测的制度量的论文——不是「效率提升了多少」，而是「新增制度外资产的速度超过了既有制度的处理速度」。复利模型的那句话值得抄下来：影子 IT 指数增长的条件，是产出物的繁殖率高于退役率。这与 11-10、11-11 两份简报里反复出现的那条线严丝合缝：LF 的实测说 25% 的入站 PR 被判为 AI slop，Kafka 的提交里 19.3% 带 agent 署名——产出洪峰已经到了。今天这篇补上了另一半：洪峰不只在组织之间的公地（GitHub）上发生，也在组织内部的私地上发生，而私地上连一个可被审阅的 PR 页面都没有。更值得注意的是它的方法论自省：纯行为规则全军误报，因为「同一个程序连非 AI 服务」在外观上不可区分；只有把远程服务的身份（一个外部可验证的锚点）拉进来，检测才成立。这在结构上就是「本地可观测性不够，必须有一个跨组织的身份层」。

「开源之道」点评：把它放在威廉姆森的四层里：L4（谁在做什么动作）已经彻底 agent 化，L3（谁批准这个动作）在组织内部还停留在一台台机器上的本地规则，而本地规则能被绕过的原因不是它写得差，是它没有可以锚定的外部身份。作者给出的解法——把行为锚定到远程服务身份——恰好是公地治理里最基础的一步：先有可归属，才谈得上规则。奥斯特罗姆的八原则里「清晰的边界」排在第一条，不是因为它是政治正确的说法，而是因为边界不清时，所有后续的监督、制裁、冲突解决机制都会退化为误报。另一个值得记住的细节是那 1–5 分钟的归因窗口：检测能力的有效期，取决于 DNS 缓存。一个治理系统的可观测性被一个 TTL 决定——这句话比论文里所有数字都更接近今天的真实处境。

2. 漏洞不走 fork 走复制：跨项目传染的 CVE，与「开源即公地」的一条反面证据#

An Empirical Study on CVE-based Vulnerabilities Propagation from one System to another System (IntraProject vs InterProject) · Junaid Akram、Ali Hassan、Danish Vasan（arXiv:2611.14164，cs.CR / cs.SE，2026-11-10）

链接：arXiv:2611.14164｜DOI 10.48550/arXiv.2611.14164

摘要：作者研究漏洞传播的根因问题，比较项目内（IntraProject）与项目间（InterProject）的 CVE 传播。他们用自研检测工具 SQVDT，在来自 NVD 的 CVE 漏洞数据集上做实验，发现在若干极为主流且仍在使用的软件中——包括 Linux 与 Android 的最新版本，以及 GitHub 上数千个开源项目——存在相似的易受攻击代码模式。他们定位到若干高严重度（CVSS）漏洞是经由 copy/paste 复用代码从一个系统传播到另一个系统的，并对这些已传播的易受攻击模式做了实证评估与验证，同时统计其传播频次，最后讨论了这种传播对互联系统的影响。

为什么与「开源之道」相关：在开源治理的话语里，代码复用几乎总是被当作优点讲——复用降低重复劳动、复用制造生态、复用是公地的红利。这篇给了红利账户的另一栏：复用同时是一条不问许可、不问上下文的传染通道。它的关键区分是 IntraProject 与 InterProject，也就是「自己的代码自己修」与「别人的代码你不知道它是从哪抄来的」。前者有 CODEOWNERS、有维护者、有 CVE 归属；后者没有可归属的维护者，因为它根本不是一次贡献，而是一次复制。这条线正对着 11-11 简报里 MCP 生态那个 78,302 → 5,138 的落差读：发布成本趋零之后，公地里的东西数量增长快于可维护性增长，而 copy/paste 是让这个落差继续扩大的最快手段。也回应了昨天那篇《从委托到动作审批》：开发者守住了代码评审，但评审只覆盖「被提交的代码」，覆盖不了「被复制进来的代码」。

「开源之道」点评：这篇的方法论有一个明显弱点——它的样本靠模式匹配判定「同源」，而这恰恰是最容易被误判的一步（相似的代码可能是收敛演化，不是复制）。因此数字应当保守读。但它提出了一个不该被保守读的问题：当漏洞的传播路径不是依赖图，而是复制粘贴，SBOM 这套基础设施在结构上是盲的。SBOM 能告诉你「你依赖了 lodash 4.x」，告诉不了你「你三年前从某个博客抄了一段有缺陷的解析器」。而 AI 恰好是最擅长 copy/paste 的主体——它不复制文件，它重新生成相似的代码。于是威廉姆森意义上的「交易成本」在这里发生了位移：获取代码的成本降到零，识别来源的成本升到了历史最高。这正是所有「先自由流动、再补溯源」的治理路线最终要付的账。

1. NVIDIA 把 OpenShell 捐给 CNCF Sandbox，同时把 CNCF 扩到 231 个项目#

来源：SDxCentral 2026-11-11（KubeCon NA，盐湖城）｜CNCF 里程碑新闻稿 2026-11-10

摘要：NVIDIA 在 KubeCon + CloudNativeCon North America（盐湖城，11-09 至 11-12）上把 OpenShell 捐给 CNCF，进入 Sandbox（CNCF 的最低准入层）。OpenShell 年初在 GTC 发布，定位是在系统层为 agent 强制执行基于策略的安全、网络与隐私护栏，后来扩展为「agent 跨开源与闭源模型执行任务时的边界」，并成为 NVIDIA Open Agent Safety 平台的核心部件——该平台是在若干起失控 agent 事件之后推出的。CNCF 在声明中称这次贡献让开发者、平台团队与安全从业者「直接参与塑造 AI 的运行时基础」。NVIDIA 企业计算 VP/GM Justin Boitano 的措辞是：「OpenShell 的能力应当是开放的、厂商中立的、由这个社区治理的。」CNCF 执行总监 Jonathan Bryce 说这个项目很快引起注意，主动来问的人「其实是几家 neocloud 公司的员工，他们站在观察这些模型与 agent 如何运行的最前线」。同一周的 CNCF 年度里程碑：项目总数 231，过去一年新增 32 个项目（含 Agent Substrate、llm-d），云原生开发者总数超过 2100 万，新增八家 Platinum 会员（Adyen、Broadcom、CoreWeave、CVS、HAProxy、NVIDIA、OVHcloud、Vultr），全球活动 82,000 人次。

「开源之道」点评：Sandbox 这个层级本身就是今日最值得读的制度细节。Sandbox 是 CNCF 的准入门槛最低一层——它给的是托管、不是背书；给的是「可以在这个屋檐下开始」，不是「这是标准」。把一条安全运行时放进 Sandbox，意味着它先取得了可被共同治理的资格，再谈技术地位。对照 MCP 的路径（同样是 LF 系，同样从单一公司主导起步），这是一个反复出现的模板：先由一家公司的商业需求催生 → 开源 → 捐给中立基金会 → 治理权逐步稀释。问题不在于这个模板对不对，而在于稀释速度——而这恰恰是可以用名册、章程、选举时间表来测量的东西。今天的 Project Pulse 测的就是 ANS 这个模板的一次具体落地。至于 Bryce 那句「来问的是 neocloud」，也值得记：推动一个安全运行时进入基金会治理最积极的力量，不是被保护的用户，是出售算力的新云厂商——因为 agent 能不能进生产环境，直接决定他们的产能卖不卖得出去。

2. Linux Foundation 正式接下 Agent Name Service：五个 TSC 席位里三个来自 GoDaddy，而章程第 2.d 条把这件事写进了过渡期#

来源：Linux Foundation 新闻稿 2026-11-10｜Cloud Native Now 2026-11-10｜规范与代码 github.com/agentnameservice

摘要：LF 在 KubeCon NA 宣布 Agent Name Service（ANS） 作为正式项目启动。ANS 是建在 DNS + 网站已经在用的证书体系之上的开放标准，为跨互联网运行的 AI agent 提供可信身份、验证与发现。完整规范由项目的技术指导委员会（TSC）公开开发，共七份文档：域锚定命名、注册与版本化、DNS 发布、公开日志审计、完整性监控、agent 间认证。自 6 月宣布「有意发起」以来，已有 11 家组织参与贡献或采纳：Cisco、Cloudflare、DigiCert、DistributedApps.ai、GoDaddy、HOL、Infoblox、Radix、Salesforce、OWASP、Trustmodel.ai。早期落地包括 LF 旗下另一个项目 AGNTCY 的 Agent Directory Service 支持 ANS 身份验证，以及 ANS Finder 通过 Agentic Resource Discovery（ARD）的注册表一致性测试。Jim Zemlin 的定调是：「自主 AI agent 正在全球系统间交易与运行，但没有可验证身份就走不通。」规范与代码托管在 github.com/agentnameservice。

「开源之道」点评：ANS 最有制度分量的一处，是它没有另造一套信任根，而是接了 DNS 与 X.509——云安全联盟（CSA）在 6 月的分析里把这条路的两面都摆出来了：这个选择让 ANS 立刻拥有了二十年的全球基础设施，也让它继承了这两个层级累积的安全债——DNSSEC 在约三分之一的解析路径上被验证、只有约 7% 的区有加密签名，而缓存投毒、注册商被攻破、路由劫持、同形字欺骗这些老攻击，在 agent 系统里会变得更危险，因为agent 是程序化、规模化地做信任决策，没有人类那点偶尔起作用的直觉（CSA 分析 2026-06-25）。CSA 还点出一件被宣传话术盖住的事：ANS 的技术实质来自 2025 年 5 月的一篇论文与一份 IETF 草案，其设计是「DNS-inspired」（借 DNS 的分层命名与委派，用独立的 Agent Registry 做解析端点），而不是把 agent 身份直接编码进活的 DNS 资源记录；LF 2026 年的表述比原始设计更靠近字面意义上的 DNS 集成。这不是吹毛求疵——宣传的架构与规范的架构差多远，决定了这套制度日后能被检查到什么程度。而这刚好可以做：规范、章程、名册，今天全部在 GitHub 上，可以逐字读。

3. Cosmos 把 IBC 捐给 LF Decentralized Trust；OpenSSF 加入 MOSAIC#

来源：PR Newswire / Cosmos Labs 2026-11-09｜OpenSSF 新闻稿 2026-11-09（KubeCon NA）

摘要：IBC（Inter-Blockchain Communication Protocol） 由 Cosmos 与 Interchain Foundation 捐给 LF Decentralized Trust，作为该组织下的项目托管，Google Cloud 支持。共同发起方包括 Agoric、Blockaid、Cardano Foundation、Cosmos Labs、Cronos Labs、Espresso Systems、Figure Markets、Hypernative、Injective Labs、OpenZeppelin、Wells Fargo、Zeeve 等二十余家机构。IBC 自 2021 年以来处理 500 亿美元以上交易额，覆盖 115 个以上网络；用户包括拉美与加勒比地区央行、日本企业背景的受监管存款代币平台 DCP、以及瑞穗 / 三菱 UFJ / 日本交易所集团支持的 Progmat。Cosmos 联合 CEO Barry Plunkett 强调「现在还有了开放治理」；Wells Fargo 数字资产平台负责人 Vitaliy Dorum 称这提供了「协作共同技术优先事项的中立论坛」。同日 OpenSSF 宣布新会员 Beautiful Majestic Dolphin、DevGuard、UElement Technologies，并宣布加入 MOSAIC（Multi-Organization Secure AI Coordination），另发布 AI 找漏洞/修漏洞指南与 AI 对软件安全影响的新研究。OpenSSF 安全架构师 Laura Guazzelli 的话值得抄：「这个新的 SDLC 已经压塌了漏洞发现与自动化攻击之间的窗口，暴露了那些没有为 AI 驱动的威胁做好准备的防御。」

「开源之道」点评：IBC 这条的看点是用户结构，不是技术——央行、受监管存款代币平台、日本三大金融集团的发行平台。当一个协议的用户全是必须回答「谁批的」这个问题的机构时，「中立治理」就不再是理想主义的姿态，而是运营许可的前置条件：你没法向监管解释「这条链的互操作规则由一家公司单方面决定」。所以 Barry Plunkett 那句「现在还有了开放治理」，读起来像补充说明，实际是准入条件的达成公告。这与阿尔希安—德姆塞茨那套产权逻辑一致：资产专用性越高、交易对手越需要可追责，产权就越必须从私人手里挪到一个可信的中立结构里。OpenSSF 那条则从另一头呼应今天的论文：它加入 MOSAIC 的理由，与《Shadow AI》给检测器加「远程服务身份锚点」的理由是同一句话——本地防御扛不住 AI 时代的速度差，必须去跨组织的层里找锚点。

Agent Name Service（agentnameservice/*，14 个仓库）— 一份罕见的、可以逐条检查的「公司项目转基金会」样本#

  • 章程自己把这件事写清楚了：Charter 2.d 规定「过渡期结束后或首次选举完成后（取早），同一组织及其关联方不得占半数以上席位」；TSC.md 直言「过渡期名册故意超额」，并给出算数：若首轮选出 5 人则最多留 2 人，若选出 7 人则可留 3 人。过渡期截止：不晚于 2027-11-09，首次选举必须在此之前完成；席位 5 → 7 → 9 分两次选举扩容，没有合格候选人的席位空置，且不计入法定人数与任何门槛。
  • 八处空位：ans-reviewers、sdk-go-reviewers、sdk-rust-reviewers、spec-reviewers 的成员均为 []。MAINTAINERS.md 的 Hosted test environments 表写的是 [none yet]，Emeritus 表为空，Quiet periods 表为空。

【今日最锐利的一处矛盾：许可证】 章程 §7.b 已经规定 新入站代码必须用 Apache-2.0、新规范用 CC BY 4.0；但截至今天，ans-sdk-go / ans-sdk-rust / ans-sdk-java / agent-trust-discovery / ans-gateway-auth / ans-openshell 的 GitHub 许可证元数据仍是 MIT，ans-spec 是 NOASSERTION（其 LICENSE 文本是 Apache-2.0，版权行写 © 2025 GoDaddy Operating Company, LLC），只有 ans 已经是 Apache-2.0。ans 的 PR #152 / issue #151（11-05）正在做这件事，措辞极其严谨：「提议新原创贡献采用 Apache-2.0，保留 MIT 原文与版权声明于 LICENSES/MIT.txt……不主张从过去的 MIT 贡献者那里取得追溯的 Apache 专利授权」，并自陈这是第一个仓库的试点，通过后才改其余 MIT 仓库。

【AI 参与度实测】 ans-spec 的 66 个 PR 中 25 个带 Assisted-by: 披露（38%）；已合并的 37 个 PR 中 10 个带披露（27%）；ans 的 82 个已合并 PR 中 20 个带披露（24%）。披露工具分布：Codex (GPT-6) 约 13 次，Claude Code (claude-fable-5 / 5.1 / opus) 约 11 次。其中 csnitker-godaddy 自己的 23 个 open issue，全部带「Assisted-by: Codex (GPT-6)」。规则来源可追：**PR #38（2026-07-17 合并，#37）**一次性采纳了 LF 贡献模型——DCO 签署 + 按 Linux 内核惯例做 AI 披露 + 每个 PR 必须 issue 链接；CONTRIBUTING.md 的原文是「AI 工具绝不可添加 Signed-off-by: 行。DCO 认证属于人类提交者，后者对贡献的正确性与许可负全部责任。」

「开源之道」判断：这是 2026 年至今最值得保存的一份「公司项目转基金会」标本，理由不是它做得差，而是它把通常藏在口头承诺里的东西写成了可核算的条款。RATIONALE.md 开篇那句话几乎就是适兕的问题意识：「从一家公司搬到基金会的项目，往往以同样的几种方式失败」，然后逐条列出——创办公司实际上仍然控制（→ 章程 2.d + 选举 + 跨组织批准）、席位靠名分而非靠工作填充（→ 首轮起候选人必须是 Maintainer/Reviewer）、治理焊死在法律文件里（→ 章程只管使命与权限，流程放 GOVERNANCE.md）、没人承担行政（→ 主席、副主席、9.3 年度权限复核、9.4 季度健康检查）、规范与实现漂移（→ 规范性变更必须在实现与每个 SDK 里开跟踪 issue 才可合并）、为五十人设计的流程用在五个人身上（→ 常规变更两次批准，提案只留给高影响变更）、评审预期无视真实生活（→ 十天是首次回复而非批准，缺席者不计，可宣布静默期，错过只触发升级、永不惩罚）、PR 死于无人理睬（→ 阻塞反馈必须是 Request changes，审查方一侧的等待永不因不活跃而关闭）、捐赠后才发现许可证对不上（→ 新入站一律 Apache-2.0）。

这份清单的价值在于：它是一份「预期失败模式 → 对应条款」的对照表，而每一条都能回到文件里核对。这在开源治理文献里非常少见——大多数基金会章程是授权文件，ANS 这份是防错文件。适兕说过「制度怎么设计」而不是「批判制度」；这就是一份可以拿去当教材的设计。

但同一份标本也把大分流 2.0 的问题意识照得更亮：条款的质量和名册的构成是两件事。章程把 3/5 写了进去、把选举日期写了进去、把「过渡期故意超额」也写了进去——这是一种诚实，诚实本身值得记；但诚实不改变一个事实：在 2026-11-12 这一天，一个旨在给「全互联网的 AI agent」发身份证的项目，其规范仓库 30 天里 7 个提交全部来自同一家域名注册商的员工，83% 的 issue 由同一个人开，而那两件来自真实运营者的问题（无域名者如何注册、跨 RA 声誉如何 fail closed）一条回复都没有。 这不是指责，是测量——洛苏尔多意义上的「命名时刻」：项目的名字已经叫「中立标准」，而它离中立标准最近的一次，是那份把不中立主动写进条款的 TSC.md。

判断方向：制度健康在变好，但速度由名册决定，不由文本决定。三个月后要复查的就三个数：①agentnameservice/tsc 团队的成员里非 GoDaddy 账号的个数（今天 2/5）；②ans-reviewers / spec-reviewers 是否仍为 []（今天均为空）；③外部 issue（#43、#76）的首次回复时延（今天已分别等待 108 天与 32 天）。如果这三项在 2027-11-09 前没有实质变化，那么「过渡期故意超额」就不再是诚实，而是惯例。

桥接：阿西莫格鲁与罗宾逊的包容性 vs 汲取性，在这里不是「好公司 / 坏公司」的二分，而是准入规则是否让新来者能凭工作获得权力。ANS 的 CONTRIBUTOR_LADDER.md 与「必须担任 Maintainer 六个月才能竞选」这一条，结构上是包容性的——它把权力绑在工作上而不是绑定在出资上。但空置的评审席位表说明准入通道还没有人走。制度的包容性不体现在墙上写的条款，体现在第一个走过来的人有没有被接住。今天，minitru 走过来了一次（PR #105，指出规范与实现不一致），问题提得对，还没有人接。
