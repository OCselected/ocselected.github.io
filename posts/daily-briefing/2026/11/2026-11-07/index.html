「开源之道」 2026-11-07 搜集事件和材料#

今天这份，落在同一条线的第六个剖面上：能走的人带不走东西，能带走东西的人不必走。

① 先看一个残酷的实验。 Douglas Cumming 把 2015–2026 年 Retraction Watch 记录在案的全部 57 次编辑部集体辞职做了统计。在 19 个涉及更换主编的事件里，董事会集体辞职之后，产权人一次都没有让步。这不是道德故事，是产权结构的读表：一群人掌握全部专业能力、掌握全部声誉来源、随时可以走——对面那个人不掌握任何专业能力，只掌握产权。结论只有一句：专业能力不构成谈判力，能带走的东西才算资产。

② 再看一个更细的切分。 牛津与比勒陀利亚等机构的作者提出 PAAI 框架（Power、Access、Adequacy、Independence），去量"谁真正有权独立评估 AI"。12 个非洲 AI 评估项目，加上国际 AI 安全研究所网络三次联合测试中 10 个成员机构的分工，反复出现同一个三分布局：榨取式协作、依附式创新、受限的独立。原文那句值得抄在墙上——“设计权而没有基础设施权，从未产生超过局部的独立性”。参与的层级决定参与的重量：写数据、做标注是 L4 层；定框架、控基础设施才是 L3 层。

③ 然后是门禁自己。 一篇预注册实验量了 AI 代码修复的漏网率：只有典型输入的全断言门禁，放行了 41.0% 的错误修复；把一条从 release note 里写出来的边界输入加进去，降到 6.5%；即使把测试菜单扩到 1491 个片段加 233 个硬干扰项，仍有 15%–17% 的硬错误通过。最有效的那个修法，是整个实验里最不需要算力、最不需要模型的：它需要的是读懂变更说明的人。

④ 三件事加起来是一件事。 辞职带不走刊名，参与换不来基础设施，门禁管不到自己没写过的边界——它们都是"你以为你拥有，其实你只是被允许使用"的不同版本。今天的两条动态恰好在旁边作证：Google 把 gVisor 捐给 CNCF，理由不是相信开放，而是上游 Linux 维护者拒绝在厂商拥有项目期间合并补丁——产权归属一换，协作成本就下降；百度 ERNIE 5.5 的许可证则把"开源"写成了一张准入表，地域、营收、署名全是变量，唯一不变的是许可方的裁量权。

所以今天真正想说的是：判断一件事属于谁，不要看谁在做，要看谁能在不做之后仍然保有它。 开源世界里最常被误认的进步，是"你被邀请参与讨论、被列为贡献者、被写进致谢"；而度量口径、发布节奏、仓库域名、基准集仍在别人手里。这不是谁恶意，是基础设施权的自然分布——谁出机器、谁管数据管道、谁定发布窗口、谁持有产权。真正把权力往下放的路径，从来不是争取更多"参与名额"，而是自己建一套能跑起来的东西，哪怕它初始很差。这也是开源之所以重要的唯一理由：它是少数能把基础设施权往下交的机制。而它能交到什么程度，取决于它自己有没有勇气承认——LICENSE 保证你能用、能改、能分发，它从不保证你能参与决定。

1. 当一个能辞职的董事会遇上一个不能辞职的产权人#

  • 标题：Owning What Can Quit: On the Governance of Scholarly Journals
  • 作者：Douglas Cumming（约克大学 Schulich 商学院 / 佛罗里达大西洋大学）
  • 链接：arXiv:2611.02302｜DOI 10.48550/arXiv.2611.02302（econ.GN，2026-11-01 提交）
  • 摘要：这篇论文研究的不是开源，却是今年读到的最锋利的"公地治理失败在时间维度上展开"的实证。作者构造三组数据：①Retraction Watch 记录的 2015–2026 年全部 57 次编辑部集体辞职；②110 本经济、金融、会计期刊的编辑任期记录；③期刊层面的发表与收入数据。三条发现：(a) 辞职不能逆转产权人的决定——19 个涉及更换主编的事件里，董事会集体辞职后产权人一次都没有让步，编辑共同体的影响力只存在于"离开之前"那一刻；(b) 离开的董事会能否带走期刊声望，取决于董事会之外的制度——继任期刊（successor journal）在有学会背书的地方最常出现，在非营利主机构稀缺的医学领域极少出现，而期刊排名榜评估的是"刊名"而不是"编刊的人"，所以声望留在产权人手里；(c) 任期限制被"按产权人的意思"执行——在该限制被执行的期刊，产出几乎翻了四倍，短期收益明确，长期对声望的影响尚不可知。
  • 为什么与开源之道相关：这是"公地 vs 产权"最纯粹的对照实验。一群掌握全部专业能力、掌握全部声誉来源、随时可以走的人，遇上一个不掌握任何专业能力、但掌握产权的人。这恰恰是开源世界里反复出现的结构：维护者在治理冲突里"退出"，但退出者带不走项目名、带不走仓库、带不走域名。
  • 开源之道视角点评：奥斯特罗姆讲公地要有人自己定规则、自己监督，但她没有讲透一件事：公地的成员资格是可以被收回的，公地本身的产权却不是。这篇论文测出了那个不对称——57 次集体辞职，0 次产权人让步。开源社区把"分叉"（fork）视为最后的武器，正是因为它试图在产权层面重新划一条线：不是退出，而是复制。但 fork 的历史记录同样不乐观，声望、下游、命名权往往跟着原仓库走。所以真正的问题不是"社区有没有退出权"，而是社区退出时能带走什么——这一条，比许可证条款更决定公地的命运。另一点方法论上的收获：它用"是否出现了继任期刊“作为影响力的代理变量，这比问卷调查可信得多——制度分析里最可信的信号，永远是已经留下的痕迹。

2. 参与评估不等于拥有评估：PAAI 框架与"贡献了数据、没拿到权力”#

  • 标题：Who Can Evaluate AI Independently? A Framework for Analysing Evaluation Infrastructure
  • 作者：Sumaya Nur Adan、Joanna Wiaterek、Nourhan Abdelrhim、Sydney Reis、Robert F. Trager、Benjamin Rosman、Marina Jirotka（牛津 / 开普敦 / Wits 等）
  • 链接：arXiv:2611.08134｜DOI 10.48550/arXiv.2611.08134（cs.CY / cs.AI，2026-11-05 提交）
  • 摘要：论文提出一个四维框架 PAAI（Power、Access、Adequacy、Independence），用来追问"谁真正有权独立评估 AI"：谁控制评估基础设施、以什么条件开放、这种基础设施是否足以支撑评估目的、它支持多大程度的自主。作者把它套在两组对象上：2022–2025 年12 个非洲 AI 评估项目，以及国际 AI 安全研究所网络已发布的全部三次联合测试中 10 个成员机构的分工。结论是一个反复出现的三分布局：榨取式协作（extractive collaboration）、依附式创新（dependent innovation）、受限的独立（constrained independence）。非洲机构大量贡献数据、语言专业能力与任务设计，而外部机构保留对基础设施与评估框架的权威；设计权而不带基础设施权，从未产生超过局部的独立性。即使在以高收入国家为主的联合测试里分工同样如此：牵头某个测试的机构同时运行被评估的模型；网络里唯一的非洲成员肯尼亚从"标注"走到"任务设计"，但没有任何有记录的模型执行。一句话结论：参与评估本身不产生评估权威。
  • 为什么与开源之道相关：这是阿西莫格鲁"包容性 vs 汲取性制度"在 AI 治理领域最干净的当代应用，而且它把"包容"拆成了可测量的四层。它同时回答了开源世界一个悬而未决的问题：为什么"我们也参与了标准制定"往往不改变结果——因为参与的层级决定了参与的重量。
  • 开源之道视角点评：“设计权而没有基础设施权，从未产生超过局部的独立性”——这一句值得抄在墙上。开源社区里最常被误认的进步就是这种：你被邀请参与讨论、被列为贡献者、被写进致谢，但度量口径、发布节奏、基准集仍然在别人手里。这不是谁恶意，而是基础设施权的自然分布：谁出机器、谁管数据管道、谁定发布窗口。想要真正的独立性，路径不是争取更多"参与名额"，而是自己建一套能跑起来的评估基础设施——哪怕它初始很差。这也是开源之所以重要的原因：它是少数能把基础设施权往下放的机制。用威廉姆森的分层说，这篇论文实际量的是 L3（治理机制）与 L4（资源配置）之间的落差——在 L4 上贡献得再多，也不会自动上移一层。

3. 「验收通过但是错的」：41.0% 的静默放行率与门禁的门槛在哪一层#

  • 标题：Accepted but Wrong: Silent Failures of LLM Code Repairs after API Migrations
  • 作者：Xiaobo Chen、Genliang Zhu、Ziyuan Wang、Chu Wang
  • 链接：arXiv:2611.08269｜DOI 10.48550/arXiv.2611.08269（cs.SE / cs.AI，2026-11-05 提交）
  • 摘要：预注册实验，73 个修复任务，覆盖 CPython、Node.js、SQLite 的 60 处已记录 API 变更；每个候选修复都在真实运行时上跑，并用"未公开的契约"（withheld contracts）验收。核心数字：只用典型输入的全断言门禁，放行了 41.0% 的错误修复。把一条从 release note 里写出来的边界输入加到门禁里，降到 6.5%（在 15 个未见的聚类上 6.1%）；让一个从未见过程序的盲写者写三条输入，也能降到 7.0%。但进一步扩大测试菜单（1491 个片段 + 233 个在典型输入上与旧输出一致的"硬干扰项"）时，仍有 16.8% / 15.3% 的硬错误程序通过。自检（self-tests）帮助较小。跨四个模型族，边界输入在三个开放权重族、三套菜单上一致地把"每次尝试的错误放行率"从 0.233 压到 0.057，且不降低正确完成率。
  • 为什么与开源之道相关：这是把"测试即治理"推到极限的一篇。开源项目的合并门禁，本质上就是一套自定的验收规则 + 自定的监督（奥斯特罗姆原则 3 与 4 的软件版本）。这篇论文的量级说明：门禁的强弱不取决于规则存在与否，而取决于规则是否覆盖到边界——而边界恰恰是 release note 里写、测试里不写的那一部分。
  • 开源之道视角点评：41% 这个数字，如果放到企业 OSPO 的"AI 生成代码合规"话术里，几乎是一种消解：你以为你在审代码，其实你在审"典型输入的通过率"。而论文给的最优解——一条从文档里写出来的边界输入——恰恰是最不需要算力、最不需要模型的解，它需要的是读懂变更说明的人。这是对"AI 让开源贡献变便宜"这一叙事的反面补充：便宜的贡献让门禁压力上升，而门禁的加强几乎完全依赖人的判断力，而不是更多 AI。制度上，这意味着下游项目（消费方）承担了上游 AI 加速的外部性，而它们原本就没有多余的 reviewer。另有一个细节值得留下：“自检帮助较小”——被检验者自己补的测试，几乎不改变漏网率。这与本报 11-05 的 Foresight-SWE（agent 预见不到自己引入的缺陷，FRR 6.13%–24.53%）和 BOBA（自判正确率 53%）构成同一结论的第三个独立样本：核验的价值来自核验者的外部性，而不是核验的强度。

1. Google 把 Agent Substrate、gVisor、OpenRL 捐给 CNCF：一次「因为上游不合并」的捐赠#

  • 来源：Google Cloud Blog（2026-11-05）｜Google Open Source Blog（2026-11-05）
  • 原文：Open infrastructure for autonomous agents comes to CNCF｜Sandboxing untrusted AI agents at scale

Google 在 KubeCon NA（盐湖城，2026-11-05）宣布把三个自研开源项目捐给 CNCF Sandbox：Agent Substrate（有状态 agent 运行时，actor/gateway 与 warm worker 池解耦，空闲会话 500ms 内恢复，10 倍容器密度，1.0 已 GA 于 GKE）、gVisor（用户态内核沙箱，隔离未审查的生成代码）、OpenRL（Kubernetes 上的自托管 RL 后训练）。动因写得很直白：沙箱基础设施提供方（包括 Google）都维护着让 gVisor I/O 接近原生 Linux 的主机内核补丁，但上游 Linux 维护者拒绝在一个厂商拥有项目期间合并它们。捐赠后，Ant Group、Modal、Tines 加入成为 maintainer。

「开源之道」点评：这是今年读过的最诚实的一份捐赠声明——不是因为"相信开放"，而是因为"所有权挡住了合并"。它是一个教科书级的制度观察：同一份代码，产权归属一换，协作成本就下降。有意思的是它同时暴露了基金会机制的另一面：CNCF 在这里不只是中立托管方，它还是"提供合法产权转移通道"的机构，而这条通道的通行券，恰好是"上游拒绝"。这与 2026-10-26 那批公司捐赠项目的规律一致：治理权转移需要合法通道，而通道打开的时刻，往往是大厂自己遇到了结构性的协作阻塞。

2. 百度 ERNIE 5.5 Flash Base：把「开源」缩成一个地域与营收的函数#

  • 来源：Hugging Face 模型卡与许可证原文（2026-11-05）｜ChinaTechNews（2026-11-06）
  • 原文：模型卡｜LICENSE 全文

百度于 11-05 在 Hugging Face 发布 ERNIE-5.5-Flash-Base（280B 总参 / 14B 激活的稀疏 MoE，33.5T token 预训练，128K 训练上下文，微调与推理可扩到 1M），是预训练终点、未经 mid/post-training 的 base checkpoint。HF 元数据实测：license: other，license_name: ernie-5.5-flash-base-model-license-v1.0，仓库 2026-10-21 创建、11-05 最后更新，208 likes / 526 downloads。媒体口径称之为"开源转向"，但许可证全文不是这么写的。实测四条硬约束：

  • §1.11 Territory = 全球除去欧盟、英国、韩国；§5.3 明确"在 Territory 之外使用、复制、修改、分发、展示"均不授权。
  • §1.7 / §4.2 / §4.3 营收门槛：使用该模型（或其衍生模型）的相关产品与服务，按同一 Operator 及其 50% 以上控股关联实体合并计算的连续 12 个月营收，超过 5000 万美元必须事先取得书面商业授权，且未获授权期间必须暂停使用（§4.3(b)：申请、等待、磋商都不构成授权）。
  • §3.2 强制署名：“Powered by ERNIE” 必须出现在 UI、官网、关于页或产品文档的显著位置；§6.3 只授予为履行该条所必需的商标使用。
  • §5.5 反蒸馏：不得用该模型或其输出改进除本模型及其衍生模型之外的任何 AI 模型。

对照：ERNIE 4.5（2025-06-30）十个变体走 Apache 2.0（无地域、无营收门槛、无署名要求）；ERNIE 5.0（2025-11）没发权重。

「开源之道」点评：这不是"开放权重"，这是把许可证写成了一张准入表：地域是变量、营收是变量、署名是变量，唯一不变的是许可方的裁量权。开源定义（OSI）里有六条硬门槛，其中两条在这里被直接撞穿——不得歧视使用领域、不得歧视个人或群体（§1.11 按法域切分）。所以把它叫"开源"是范畴错误，准确的描述是有条件的可得性（conditional availability）。这里不需要任何民族化叙事：只需要读许可证。§5.5 那条反蒸馏尤其值得记下——它把"从输出中学习"判为违约，这是比 copyleft 更强的一种输出侧产权主张，而开源世界的互惠逻辑（copyleft）约束的是分发，不是学习。两者不是同一件事，混为一谈会让"开放"这个词彻底失去检验标准。

3. Unleash：十一年 AGPL 的 feature flag 服务器，治理文档为零#

【L2 · 治理结构——今天真正的信号】 gVisor 的治理是少见的激进的反俘获设计，而且全部可复核：

  • Org-balanced voting（GOVERNANCE.md §Voting）：对四类决定——修改治理文件、maintainer 任免与复职、战略方向与路线图排序、以项目名义发布官方回应——每个组织（雇主）只有一票，不论它雇了多少 maintainer；独立贡献者各得一票。票数按组织计，不按人头计。
  • 僵局解决条款：如果组织票 55 对峙，则回退到人头计票，人多者胜；仍相等则提案失败。因此 charter 要求 maintainer 记录每个人怎么投，而不只记录组织怎么投。
  • Maintainer 身份与雇主解绑：Values 明文写"maintainer 以个人身份持有该角色，不代表其雇主，换雇主后保留该角色"。
  • 名册即代码：governance/maintainers.yaml 为唯一真源（含 affiliation、past_affiliation、status、areas），MAINTAINERS.md 与 CODEOWNERS 由生成器产出（CODEOWNERS 文件头明确 “do not edit directly”）。areas.yaml 逐区标注 enforced_review，决定该区是否强制专业 reviewer。

【开源之道判断】 gVisor 现在处于一个非常典型的临界状态：制度设计超前于制度事实。它的 charter 已经为"多组织共治"准备好了全部接口（一人一票按组织计、僵局回退、身份与雇主解绑、名册即代码），但事实层面仍是一个单一雇主的项目，而且刚失去一位治理工程的主要推动者进入 hiatus。制度健康的关键指标因此非常明确：未来 90 天内 maintainers.yaml 里出不出第一个非 Google 的 ACTIVE 条目。出了，org-balanced voting 就从纸面变成活的机制，捐赠才算真正完成；不出，这份 charter 就是一份写给未来看的文件——它保护的不是现在的项目，而是项目将来被动摇时的那条退路。
