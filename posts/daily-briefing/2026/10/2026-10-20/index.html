「开源之道」 2026-10-20 搜集事件和材料#

今日主线只有一句：开源的生产成本在塌陷，制度成本在上涨。 下面四条新闻和两组项目观察，都是这一句话的不同侧面。后半段的 Project Pulse 是十一个项目的全量重跑——它把这句话落到了具体的时间尺度上：秒级的自动化、周级的沉默、年级的债务。

📄 最新开源研究论文#

今日可核验的新论文数量很少。检索覆盖 arXiv（open source governance / open source AI governance）、OpenAlex（open source + institutional、contribution incentives、digital commons governance）、CrossRef（open source + commons governance）、SSRN（open source + institutional governance / AI + license，近 14 天）。近两天（10-19、10-20）能拿到全文元数据、且与「开源之道」直接对话的新论文只有一条；其余为已发表或已报道的旧文，按纪律不重复收录。

1. When Discovery Outruns Notification: The 2026 Vulnerability Disclosure Surge and the Governance of Open-Source Security#

  • 作者：Raul V. Rodriguez、Hemachandra Kannan、Pavana Kiranmai Chepuri
  • 来源：SSRN Working Paper，2026-10-18
  • DOI / 链接：10.2139/ssrn.7629481
  • 说明：SSRN 在 Cloudflare 之后经 CrossRef 索引（10.2139/ssrn.* 前缀）拿到的元数据与摘要；全文未取。

摘要：作者用 2017 年至 2026 年 10 月全部 35,263 条 GitHub 已审核 Advisory 做面板，并把 npm / PyPI 的修复版本发布日期链接进来。核心事实是：2026 年 3 月到 9 月，已审核 advisory 平均每月 1,306 条，是 2023–2025 年均值的 4.5 倍；其中 84% 由维护者本人发布。结论落在一个反直觉的位置——修复环节守住了（repair held at the point of disclosure），出问题的是「发现之后到通知之前」这一段：AI 辅助的漏洞发现让上游发现量暴涨，而通知、分诊、复现、定级仍然要靠人。

为什么与开源之道相关：这是第一次用全量规模数据（不是抽样、不是问卷）把「AI 把漏洞发现成本打到接近于零之后，谁承担了新增的转换成本」量化出来。答案很直接：维护者。这正是我在 10-19 的日报里从 Linux 内核弃用 Assisted-by、PostgreSQL 19 推迟两条消息推出的判断——审查能力成为稀缺资源——这里给出了计量证据。

开源之道视角点评：这篇论文的实证结论其实是奥斯特罗姆式的：监测（monitoring）是公地治理八原则里最贵的一项，而 AI 让监测成本下降、却让「分级与惩戒」成本上升。更深一层，它揭示了一个制度错配——安全披露体系（advisory、CVE、注册表）是围绕「发现稀缺」年代设计的，当一个制度的设计前提被技术打掉，制度不会自动调整，它只会把压力传递给链条上权力最小的一环。维护者就是那一环。

📰 开源动态摘要#

1. Siemens 关停 OpenRadioss 并删除仓库，社区 18 天内接续为 OpenCourant#

  • 来源：Phoronix, 2026-10-01、heise online, 2026-10-02、Rocky Linux / RESF, 2026-10-19
  • 摘要：Siemens 在收购 Altair 之后，于 2026-10-01 关停原由 Altair 在 2022 年以 AGPLv3 开源的有限元求解器 OpenRadioss：官网下线重定向到「转型页」，GitHub 仓库直接删除且未留归档。Siemens 的说法是把投入集中到商业产品 Simcenter Radioss 和面向「获批联合项目」的研究计划——它自己把这套叫 “Shared Source” 环境。10-01 当天社区即宣布 fork：OpenCourant，保留完整 commit 历史、继续 AGPLv3；10-05 第一批 Linux 构建上线，10-06 三个平台（Linux x86-64 / arm64 / Windows）全部打通。10-19，Rocky Enterprise Software Foundation（RESF）宣布 OpenCourant 成为第一个 RESF 孵化项目——一个按「项目治理而非公司意志」写的章程下的中立托管方。

开源之道点评：这是本周最干净的制度标本，值得拆开看三层。

第一层，许可证保护了什么。 AGPLv3 让「已发布的代码」不可撤回——任何持有副本的人可以继续使用和分发。但 Siemens 删掉的是一个协作场所，不是一份许可证。四年社区开发留在仓库里的 issue、PR、review 讨论、CI 配置、贡献者之间的默契，这些不在许可证的射程之内。许可证保护权利的存续，不保护协作的存续。

第二层，重建的代价有多真实。 heise 的后续报道里有一个细节：OpenCourant 重建交付流水线时才发现，OpenRadioss 的构建依赖内部容器 registry、私有仓库、专用构建服务器；而读取输入数据的专有二进制库根本不在 git 仓库里。是社区成员翻出归档的包，才让 ARM64 构建跑起来。长期方案是换一个 AGPL 的 reader，但它还没覆盖全部功能。这就是「开源」与「可构建的开源」之间的差额——一个项目能不能被接续，取决于它的构建路径是不是完整地落进了公地。 这跟 2023 年后的 XZ 讨论、跟软件供应链里 attestation 的紧迫性，是同一个问题。

第三层，接续需要制度承接方。 OpenCourant 没有停在「一群热心人 fork 了一个 repo」。它进了 RESF，而 RESF 的章程原文就是为「开源项目以用户没有发言权的方式改变许可证或方向」而写的——Rocky Linux 本身即 CentOS Linux 变更的产物。这里有个值得记住的递归：一个因治理失效而生出来的基金会，正在收容下一个治理失效的受害者。 章程不是抽象美德，它是被具体伤害写出来的。

RESF 给的孵化毕业条件也值得抄下来当判据：需要有社区治理模型、活跃提交者来自一个以上组织（防止单一公司或个人控制）、有项目自控基础设施上的可重复发布流程、有代码来源追踪与许可证合规。这四条就是「伪开源 vs 真开源」在治理层的操作化定义。

2. Linux Foundation 成立 BUILD Foundation，为 Bazel 维护者出资#

  • 来源：Linux Foundation 新闻稿, 2026-10-14（BazelCon, Amsterdam）
  • 摘要：LF 运营启动 BUILD Foundation，初始成员 ASML、Canva、Datadog、EngFlow、Figma、Spotify。Bazel 2015 年由 Google 开源，如今数千家公司在用，Bazel Central Registry 把规则集、库、工具的维护权分散到了生态各处。基金会首批投入针对 2025 Bazel 用户调查里排在最前的问题：雇专职技术写作者写文档、给 bazel-contrib 仓库的维护者发钱、培训认证、IDE 集成、以及在 BCR 上做发布 attestation。

开源之道点评：这件事的制度意义大于新闻意义。构建系统是开源栈里最不像产品的一层——用户不选它，用户是被它绑住的；它的产出不面向终端，只面向「能不能把代码变成能跑的东西」。这类东西在市场上天然供给不足，因为没有一个用户有足够动机单独出资，而所有用户的成本都依赖于它。这正是公共品问题的教科书定义。

ASML 的引语值得逐字读：「The BUILD Foundation lets us move from being a user to being a partner: funding maintainers, improving documentation and tooling, and helping set direction for build engineering across many open source projects, not only Bazel.」——从 user 到 partner 的身份转换，就是「消费者」到「共同产权人」的转换。 这句话比任何「开源很重要」的公关稿都更接近制度真相：可持续性不是靠感恩，是靠把使用关系改写成出资关系与治理席位关系。

同时要标注一个诚实的疑问：成员名单里六家全是重度使用方，Google 作为原始开源方不在初始成员之列。这不是指控，而是一个需要继续观察的结构：当上游开源方退出日常投入、下游使用方组队接盘，治理权会跟着钱走。 这是好事（使用者终于付费），也是风险（谁出钱谁定方向）。威廉姆森框架里，这是从 L4 资源配置层的市场交易，上移到 L3 治理层的合同安排——方向是对的，但 L3 的规则由谁写，需要盯住。

3. vLLM v0.32.0：17 天一个版本，814 commits，121 位新人#

  • 来源：GitHub Release v0.32.0, 2026-10-18、vLLM Governance Process、vLLM committers.md
  • 摘要：v0.32.0 包含 814 个 commit、363 位贡献者、其中 121 位是新人。技术主线是低精度 KV cache 全面铺开（NVFP4 跑到 SM8x/SM12x/SM90，GLM-5.x 在 SM100 上默认 FP8 KV cache）、Model Runner V2 在 ROCm 上转默认、结构化输出与通用 parser、以及一批硬件后端扩展。发布节奏：v0.30.0 09-22、v0.31.0 10-05、v0.32.0 10-18——稳定 13–17 天一个 minor 版本。

开源之道点评：放进 Project Pulse 里一起说，因为这一条的价值在治理信号而非版本号。见下文。

4. Kubernetes 2026 指导委员会换届：有效选票比 2025 年多 45%#

  • 来源：Kubernetes Contributors 官方公告, 2026-10-16、kubernetes/community 2026 ballots.csv、Last Week in Kubernetes Development
  • 摘要：7 席中 3 席改选，任期 2 年。当选：Michael McCune（Red Hat）、Janet Kuo（Google）、Priyanka Saggu（SUSE）。留任：Kat Cosgrove（VillageSQL）、Paco Xu 徐俊杰（DaoCloud）、Rita Zhang（CoreWeave）、Maciej Szulik（Defense Unicorns）。离任 Emeritus：Antonio Ojea、Benjamin Elder、Sascha Grunert。1,547 名合格选民中 308 人投票， turnout 19.91%（公告口径；我从仓库 ballots.csv 文件本身能复算出 242 行有效偏好数据，两者口径不同，以公告为准）。

开源之道点评：这次换届真正值得记的不是谁当选，是两条结构性事实。

其一，投票参与在上升。 我用 git 历史核对了仓库里的选票文件：2025 年 ballots.csv 是 167 行，2026 年是 242 行，增加 45%。公告口径的 turnout 是 19.91%（1,547 名合格选民中 308 人投票；从 2025 年的合格选民规模推算约 13–14%，量级上一致）。在一个「治理疲劳」被普遍抱怨的年代，参与度上升近一半是有意义的——它说明当选票真的能改变结果时，人们会投。这次 3 个席位有 6 名候选人，竞争率 2:1，而且结果不是走过场：第一名（elmiko）首轮 63 张第一顺位，第二名（priyankasaggu11929）57 张，中间 janetkuo 43、kaslin 47——首轮第一与第三之间只差 20 票，在 242 张有效票里这意味着排序真的在起作用。

其二，选票结构本身在说话。 我把两年的 raw ballots 都拉下来做了完整的 IRV 模拟（每一轮淘汰末位、重新分配）：2025 年，Priyanka Saggu 在首轮拿到 24 张第一顺位排第五，最终没有进入前三；2026 年她首轮 57 张第一顺位排第二，直接当选。同时，2026 年有 55 张选票把「未表态」排在所有候选人之前（首位是 6 号即 no-opinion），这是一个诚实但沉重的数字：近四分之一的投票者认为这六个候选人里没有一个值得排第一。

把这两件事放在一起，能得到一个关于 meritocracy 的判断：Kubernetes 的治理合法性来自「秘书处」而非「技术权威」。 SC 的职责写在章程里——给项目各部分划分授权、定义非技术愿景、设置透明与问责政策、作为非技术上升级的最终节点、向 CNCF 要资源。它没有一行写着「技术最强的人说了算」。 这是一个已经把自己制度化的 meritocracy：贡献换声誉，声誉换选票，选票换授权，而授权的内容被明确限制在非技术领域。这种克制，恰恰是它比很多「TSC 型治理」更稳的原因——TSC 型治理把技术判断和组织判断混在一起，一旦技术路线分歧，组织就会分裂；秘书处型治理把二者切开，技术分歧留在 SIG 里搏斗，组织只在「谁有权定义规则」这一层投票。

顺带记一笔人事结构：7 席里 Google 只剩 1 席（Janet Kuo），Red Hat 1 席，SUSE 1 席，CoreWeave 1，DaoCloud 1，Defense Unicorns 1，VillageSQL 1。没有一家公司超过 1 席——这对一个由 Google 发起的项目来说，是治理上真正完成「去发起方化」的标志。这与 10-19 的记录（Google 席位从 3 降到 1）一致，可以正式确认为趋势而非偶然。

🔍 Project Pulse#

项目一：vLLM — 快节奏与进入门槛的正面碰撞#

【L1 · 发布节奏】 v0.30.0（09-22）→ v0.31.0（10-05）→ v0.32.0（10-18），13–17 天一个 minor 版本，稳定得像钟表。这不是「发版勤快」，这是把持续交付能力本身当成了项目资产：814 commits / 17 天的吞吐，意味着主干必须长期处于可发布状态，也就是 CI、回归、发布自动化这些「非功能层」必须做到极强。9.4 万 stars、2.36 万 forks、9,091 个 open issues——issue 数不降反升，说明需求增速超过处理增速，这是有意的取舍（roadmap 优先于 backlog 清理）。

【L2 · 治理结构】 治理文档在 2026-08-06 的 PR #51300（Simon Mo）里做了一次关键改动，我拉了 commit 原文：在 Core Maintainers 段落里加了一句 “This committee is also the Technical Steering Committee as defined by Linux Foundation Project Governance.” 这句话是法律定位——vLLM 已是 PyTorch Foundation（LF 旗下）托管项目，此前 TSC 只是「in other convention, they might be called a TSC」的类比，现在变成了章程意义上的实体。同一次改动还换了 Project Leads 名单：Lu Fang、Charlotte Qi、Yihua Cheng 三人退出，Lucas Wilkinson、Xin Li 加入。

【L3 · 社区活力】 这里出现了今天最值得记的一个张力。硬件席位的扩张是可见的：committers.md 里的 AMD GPU owner 从 08-06 的 2 人（gshtras、tjtanaa）扩到 5 人（+hongxiayang、shen-shanshan、AndreasKaratzas），ROCm 也在同期成为 Model Runner V2 的默认平台。这是「谁来供养硬件后端」这个开源老问题的商业化答案：厂商派人。同时 committer 总数从 72 涨到 75。

但另一侧，进入门槛在同步抬高。治理文档里的 committer 提名标准写得很硬：需要 30+ 实质性 PR、10+ 高质量外部贡献者 PR 的 review、社区答疑、以及 RFC 领导经历，「committership is highly selective and merit based」。而文档同时写了：Ray: (unowned)。 一个 9.4 万 star 的基础设施项目，有一个重要集成方向没有 owner——这不是文件疏漏，这是维护者注意力已经在过载的体温计。

还有一处更关键的细节：vLLM 的 AI 治理条款不是「允许/禁止」，而是三条操作性规则——不要提交纯 agent PR（人类提交者必须逐行 review、端到端验证、跑测试）；必须披露 AI 参与并打 Co-authored-by: 等 trailer；避免一次性 busywork PR（单个 typo、孤立风格清理、单个 mutable default fix）要合并成清晰的系统性范围。并且这三条被写进 AGENTS.md，「with instructions for how to autonomously implement them」。 也就是说：规则面向的读者包括 agent 自己。

开源之道判断：制度健康在变好，但「好」的方向值得警惕。 vLLM 展示的是效率求生型开源的极致形态——17 天一个版本、几百人贡献、硬件厂商绑定治理席位、进入门槛用可量化指标（30+ PR / 10+ review）硬化。它极其成功，也极其脆弱：当 committer 资格变成一套可以刷的 KPI，meritocracy 就开始退化为 countocracy。真正需要盯的不是「有多少新 committer」，而是「有没有非厂商背景的人在核心子系统里拥有否决权」——Ray: (unowned) 就是答案的一半。桥接概念：阿西莫格鲁的包容性 vs 汲取性。这个项目的制度在产出上完全包容（谁都能提 PR、121 位新人进来了），但在权责分配上是集中化的（10 位 Project Leads，5 位 Lead Maintainers，都是长期核心圈）；这种「参与开放、决策收拢」的组合，是 AI 基础设施项目的普遍形态，也是下一代开源治理最需要被研究的对象。

项目二：Kubernetes — 选票是可检验的制度证据#

【L1】 无新版本信号（v1.35 周期内），今日不报。

【L2 · 治理结构】 3 席改选、6 名候选人、任期 2 年，结果已在上文列出。核心结构变化：7 个席位分布在 7 个不同组织，单一公司最多 1 席。 这是去发起方化的完成态。

【L3 · 社区活力】 有效选票从 2025 年的 167 行涨到 2026 年的 242 行（+45%），投票率 19.91%。但同期有 55 张票把「无偏好」排在所有人之前。参与度上升与「没有值得投的人」并存——这正是健康的样子：投票率低不是因为冷漠，是因为过去无差别；现在有真实竞争，参与才被激活，而同时有人诚实地表达「这六个人我都不熟」。

开源之道判断：这是今天唯一一条可以给出「制度健康明确变好」结论的信号。 理由是它可检验——ballots.csv 是公开的，任何人可以复算 IRV、可以验证 turnout、可以核对当选者。治理的可信度不来自宣言，来自候选人们能不能被独立复算。

更深一层的桥接：Kubernetes SC 的选举制，本质是把 Ostrom 的「集体选择安排」（collective-choice arrangements）落到了代码项目上——受规则影响的人有权参与修改规则。而它把权限严格限制在非技术领域，则是威廉姆森 L3 治理层的自我限定：治理机制管合同与组织边界，不管资源配置的日常决策。这种分层，比「技术委员会什么都管」要稳得多。反过来看那些把 TSC 当成全能裁判的项目——当一个组织既定义「什么代码是对的」又定义「谁有资格判断代码对不对」，meritocracy 和 powerocracy 的边界就消失了。
