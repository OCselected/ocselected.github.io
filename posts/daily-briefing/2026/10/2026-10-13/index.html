边界声明：不建立「中国开源」范畴；所有事件按可观察、可链接、可检验的具体制度安排描述（谁发布、规则要求、谁被纳入、资源如何分配、对协作行为的影响），制度判断落到具体证据，不做国家化叙事分类。

一、今日核心命题：产权置换的第二条路径——从「渗透」到「收编」#

10-12 主线是「agent 时代的 Coase 问题从理论进入运行时」（MXC GA + Anthropic 自主行为事件）。10-13 的命题回到产权结构本身——开源的产权置换第一次有了资本收编的完整路径证据：

  • HashiCorp Boundary CE 归档（2026-10-08）：IBM 收购后第一次大规模 CE→Enterprise 归档行动，最后一次 commit 是「Suppress CVE-2026-41989」（主动忽略而非修复）；
  • AWS 升 LF 白金会员 + Docsy 加入 LF + OpenGrid 发布：LF 从「软件基金会」向「AI 协议栈 + 电网物理基础设施」双向扩张，度量层/结算层/内容层/物理层四个基础设施叠加；
  • LF Europe 2026 State of Open Source 报告：31% 组织无治理框架、48% 维护私有 fork、贡献被度量但治理权重未度量——「度量权」命题获得首次大规模调查数据。

三条线索共同指向同一件事——开源产权正在被两条路径同时重构：渗透型（xz 后门、社会工程）与收编型（资本收购后停止维护）。xz 事件 2 年后无新资金进入 vs Boundary CE 主动归档——两次都是 L3 治理机制被破坏，但破坏者不同：xz 是恶意个人，Boundary CE 是收购方。这是「开源制度失效的第二种病理」第一次被数据化。

二、论文层：开放性的学术命名从「赛博庄园」到「open washing」#

📄 1. Beyond “Open Washing” – Redefining Openness for Open Source LLMs#

  • 来源：AMPROC 2025, DOI 10.5465/amproc.2025.17774abstract
  • 框架：把「open washing」定义为厂商使用 “open” 作营销标签但实质不满足真正的开放（权重、许可、训练数据、可复现性均不透明）。

具体制度安排（学术层信号）：

维度制度安排
发布主体AMPROC 2025 会议（AI/ML 政策与治理）
规则要求提出重定义开放性的多维框架（权重 / 许可 / 数据 / 可复现性）
谁被纳入LLM 厂商、开源合规审计方、AI 治理政策制定者
资源分配未详述，论文偏框架而非量化
协作行为影响把「open」这个词的可检验性拉回学术层

「开源之道」点评（大分流 2.0 命题在 LLM 时代的最新学术命名）：

  • 「open washing LLM」是「赛博庄园」的当代典型形态——适兕记忆中大分流 2.0 的「伪开源」三分类（特许工程代码 / 局域网共享代码 / 赛博庄园），LLM 权重开放但训练数据/许可证/可复现性均不透明的形态正好落在「赛博庄园」类别里。这是「赛博庄园」从概念变成学术术语的关键节点。
  • 与 10-11 Dodds & Chengyuan《Strategic Opacity》构成对话——Dodds 讨论「协议层的透明即控制」，本文讨论「营销层的开放即模糊」；两次都在用学术语言命名同一个制度现象：控制权从代码层迁移到协议层和叙事层。
  • 与适兕 AgentCon 演讲的「度量权」命题直接对话——当「open」失去可检验含义时，制度设计的第一性问题变成「谁有权定义 open」——这正是度量权命题的最原始形态。
  • 与 10-12 Beyond Productivity 论文构成学术谱系——Hill & Howison 讨论 AI 让开源协作是否可持续，本文讨论「open」这个词的语义边界正在被侵蚀。两次都在问同一个问题：开源的定义正在被谁重新谈判。

未来检验点：

  • ①「open washing」是否形成独立学术社群（跟进论文、独立会议）；
  • ②欧盟 AI Act、美国 EO 14110、中国生成式 AI 管理暂行办法是否引入 open-washing 相关的监管术语；
  • ③是否有第三方机构（如 OpenSSF、OpenChain）推出 LLM 开放性的量化审计标准。

误判风险：论文是框架性讨论，缺少「open-washing」的量化案例数据库——方法论上偏「命名」而非「测量」；作为命题命名值得收藏，作为定论需与 OpenAI、Meta、DeepSeek 等具体厂商的开放度审计交叉验证。

📄 2. Open Source Digital Sovereignty: The Case for a Canadian National Linux Distribution#

  • 来源：SSRN, DOI 10.2139/ssrn.7585538（2026-10-10）
  • 作者：Joshua Pearce

具体制度安排（学术层信号）：

维度制度安排
发布主体SSRN working paper（未同行评审）
规则要求论证加拿大应建立国家 Linux 发行版作为「数字主权」的基础软件层
证据链加拿大 60% 民众信任 USA 的民调 + CLOUD Act/FISA §702 长臂管辖 + 加拿大联邦政府对 Microsoft Windows 的结构性依赖
谁被纳入加拿大联邦政府决策层
资源分配论文未详述国家发行版的具体治理架构

「开源之道」点评（「公共基础设施所有权」命题的横向扩散）：

  • 把「操作系统作为主权资产」从欧盟政策语言移植到加拿大政策语境——10-12 LF Europe GM Carrez 说「欧洲要技术主权 ≠ 开源能自动产生欧洲主权」，本文是同一命题在北美语境的学术化表达。
  • 包容性 vs 汲取性制度的第一性问题：论文没回答「国家 Linux 发行版将由谁治理」——是政府的 OSPO（汲取性：行政指令 + 单一主体控制）还是中立基金会（包容性：多人参与 + 公开标准 + 独立治理）。这个留白才是制度设计的第一性问题——比「要不要做」重要得多。
  • 与 10-12 Huang UNC 博士论文构成互补——Huang 用 Rawls + Sen 双规范框架比较中美欧三地 AI 治理，本文聚焦加拿大 Linux 发行版的具体政策建议。两次都在把「数字主权」从政治口号推到具体制度设计。
  • Lerner & Tirole 命题的当代回响——加拿大政府要「自建发行版」隐含的假设是「上游开源不自动满足主权诉求」；这与 L-T 2002 的「非限制性许可吸引更多贡献者」的乐观叙事构成张力。当代的开源制度经济学必须同时回答 L-T 的问题（用户导向 vs 开发者导向的许可选择）和 Pearce 的问题（主权导向下的发行版治理）。

未来检验点：

  • ①加拿大政府是否在 2027 年前推出任何国家层面的 Linux 发行版项目——若无，本文的框架价值大于政策价值；
  • ②若国家发行版项目落地，其治理结构是政府 OSPO 主导（汲取性）还是中立基金会主导（包容性）；
  • ③Pearce 是否是「数字主权」学术社群的核心作者（是否已有系列产出）。

误判风险：SSRN working paper 未经同行评审；「国家 Linux 发行版」的政策成本极高，加拿大政府短期内落地的可能性低——作为命题命名保留，作为政策预测不采信。

📄 3. The openness paradox: Open-source AI and China’s quest for cyber sovereignty#

  • 来源：Dialogues on Digital Society, DOI 10.1177/29768640251376497（2025-09）

「开源之道」点评（制度置换分析在学术界的镜像）：

  • 论文用「openness paradox」描述「开源要求全球协作 vs 主权要求地域限定」的结构性矛盾，适兕在 wiki 里用的是「行政式开源」框架——框架不同（openness paradox vs 行政式开源），判断完全不同。
  • Xú Bēn「框架误导」的经典案例——同一个现象（开源与中国网络主权的张力），用不同的框架描述，得到的政策结论可能完全相反。「行政式开源」的结论是「制度性动员 + 效率优先」，「openness paradox」的结论是「结构性悖论 + 无法解决」。这是适兕 2026-08-26 明确的「制度置换分析须声明一个视角，不是定论」的学术背书。

未来检验点：是否形成「openness paradox」学术子领域；是否有跨域比较（欧洲、加拿大是否也存在类似悖论）。

误判风险：仅覆盖中国案例，样本单一——框架命名值得收藏，作为「中国独特性」的定论不采信（呼应「开源就是开源」边界）。

📄 4. Too Hot to Commit? Extreme Heat, Developer Output, and Collaboration Networks in Open-Source Software#

  • 来源：SSRN, DOI 10.2139/ssrn.7582038（2026-10-08）
  • 方法：739,587 名 GitHub 活跃用户的高频面板数据

核心发现：

  • 极端高温显著降低个人 commit 产出，且同一用户内部在随后几天基本无恢复；
  • 但在地理分散的协作对之间（跨时区/跨气候带互补），极端高温反而提升了协作效率。

「开源之道」点评（Williamson L1 社会嵌入层的正面样本）：

  • 这是「开源 = 制度契约而非技术协作模式」的最直接实证——协作行为的地理分散性本身就是制度设计。xz 后门的教训是「地理上集中的协作」，本文证明的是「地理上分散的协作」具有气候韧性。
  • Williamson L1→L4 完整因果链：L1 社会嵌入（地理分散的社区归属感）→ L2 制度环境（跨国协作的文化）→ L3 治理机制（异步代码审查、时区互补）→ L4 资源配置（不同气候带的开发者互为备份）。
  • 与第七节 LinuxStans 11/23 core projects 数据构成互补——LinuxStans 揭示「1-2 人维护」是制度失灵，本文证明「地理分散的协作对」是制度韧性。同一坐标上的正面样本和失败样本。
  • 与 10-12 vLLM 307 contributors 正面样本构成链条——vLLM 是新贡献者结构（L3 层），本文是协作韧性结构（L1→L4 层），LinuxStans 是失败样本。三次数据共同描绘「开源协作的可持续条件」的完整图景。

未来检验点：

  • ①全球气候带变化是否导致「跨气候带互补」的协作网络出现结构性重组——开源协作的地理拓扑是否会随气候变迁重新洗牌；
  • ②论文方法是否被开源社会学社群跟进（是否形成气候-协作研究子领域）。

误判风险：面板数据只覆盖 GitHub，可能低估非 GitHub 平台的协作韧性；「地理分散的协作对」这个概念的操作性定义（多分散算分散？）需查方法论细节。

三、产业层：产权置换的收编型样本——HashiCorp Boundary CE 归档#

🏭 HashiCorp Boundary CE 归档：产权置换的第二条路径（今日最强制度信号）#

  • 来源：GitHub hashicorp/boundary README（2026-10-08 更新）+ HN 50049498（83 pts）
  • 收购背景：IBM 于 2025-02 完成对 HashiCorp 的收购（$6.4B）

具体制度安排（收编型产权置换）：

维度制度安排
发布主体HashiCorp 团队（现归 IBM）在 GitHub 仓库 README 上声明
规则要求Boundary CE 不再积极开发、仓库只读、不接受新 issue/PR/社区贡献、无新 release/维护更新/bug 修复/安全补丁
谁被纳入现有用户被引导至 HCP Boundary（托管 SaaS）+ Boundary Enterprise（企业版）；开源社区 fork 被排除（无活跃替代维护者）
资源分配未来 Boundary 开发资源完全集中于 HCP + Enterprise 两条商业线
协作行为影响开源代码变成「参考实现」（reference implementation），不是「活跃社区」；社区失去了「继续演化」这一层

关键细节（值得深挖）：

  • 归档前的最后一次 commit（2026-07-31）：Suppress CVE-2026-41989（chore: Suppress）——主动忽略 CVE 而非修复。这是产权置换的最锋利证据：代码不再是生产版本，只是法律意义上的开源文本。
  • 仓库状态：仍有 4065 stars，但无 fork 到活跃社区的方向——没有第三方接手 CE 维护。
  • HN 顶级评论（sciencesama）：问「什么是好的替代品」——没有社区答案。
  • HN 顶级评论（ProblemExplorer）："IBM 的 ‘HashiCorp’ 是个笑话，‘Hashi’ 已经不在，‘IBM’ 和 ‘Corp’ 是重复的"——命名本身已经透露了制度归属。

「开源之道」点评（Williamson L3 治理机制层的产权置换教科书样本）：

  • 这是产权置换的第二条路径——「收编型」而非「渗透型」：xz 后门事件（2024）是恶意 maintainer 被社会工程攻击（渗透型），Boundary CE 归档是收购方整体停止社区维护（收编型）。两条路径共同证明：开源 L3 治理机制可以被破坏，破坏者可以是恶意个人，也可以是收购资本。
  • Williamson L3 治理机制层被破坏的具体表现：代码可读但不再演化 = 法律意义上的开源，实践意义上的关闭。「代码可读 ≠ 项目存活」——当开源失去「活跃演化」这一维度，它就成了「许可法律下的死代码」。这是「赛博庄园」的一种新形态（配合第二节 Beyond Open Washing 论文的 LLM 版本）。
  • Acemoglu「包容性 vs 汲取性制度」命题的当代对应：从包容性制度（开源社区、任何人可 fork）→ 汲取性制度（IBM 单一主体控制）的转移，不是通过代码修改完成的，是通过维护资源分配完成的——这是「产权置换」在 OSS 领域的最新形态：不动代码，动维护。
  • 与 Linux Kernel 7.3-rc7（对照样本，第五节）构成镜像——Linux 内核 30 年演化本身就是包容性制度的长期实证，Linus 主导的 merge 流程延续、6.18 LTS 已支持 12 个月、进入稳定期。Boundary CE 归档和 Linux 内核 7.3-rc7 是同一天发布的事件，两者的制度健康状态天差地别。这是「慢聚漫奏 vs 效率求生」大分流 2.0 在同一时间切片上的对照。
  • 与 Tokenomics Foundation（10-12）+ LinuxStans 11/23（今日重复追踪）构成因果链——Tokenomics 数据揭示「有 owner 的组织显示价值概率 3.7 倍」，LinuxStans 揭示「11/23 无 owner 无资助」，Boundary CE 揭示「被收购后强制变更 owner 会杀死社区演化」。三次事件合起来描绘「开源产权的可变性边界」：产权转移本身不是问题，问题是转移的接收方是否愿意承担 L3 治理机制的成本。
  • 与 IBM 其他 OSS 项目（Consul、Vault、Terraform）的关系是关键追踪点——如果 IBM 对 Consul/Vault/Terraform 采取同样的 CE 归档策略，Boundary CE 就是「IBM 收编 HashiCorp」的系统性模式；如果只有 Boundary 一例，就是单点事件。今日只有一例，需要更多样本才能定论（见第七节误判风险）。

未来检验点：

  • ①IBM 是否在 2026-11 前对 Consul、Vault、Terraform 等 HashiCorp 项目采取同样的 CE 归档策略——若是系统性模式，就是「IBM 收编 HashiCorp」的制度性证据；
  • ②Community Fork 是否出现——如果 CE 归档 30 天内出现第三方 fork 并接手维护，说明「开源的分布式韧性」仍然存在；如果没有，说明「社区无法自救」的判断成立；
  • ③HCP Boundary 的定价与功能是否覆盖 CE 用户（是否形成事实上的「开源-付费」二选一的封闭生态）；
  • ④其他被收购的 OSS 项目（Cloudflare、Cisco、Elastic、MongoDB 等）是否出现类似 CE 归档模式——是「收编型产权置换」的通用模式还是 HashiCorp 特例。

误判风险：目前仅 Boundary 一例，不足以推断系统性模式——IBM-HashiCorp 合并已有 18 个月，其他产品（Consul、Vault、Terraform、Packer、Waypoint 等）尚未看到 CE 归档迹象。作为「产权置换的第二条路径」的命名保留，作为「IBM 收编 HashiCorp 系统性模式」的定论不采信。

五、LF Europe 2026 State of Open Source in Europe：「贡献度 vs 治理权」断层命题的量化证据#

  • 来源：LF Research + LF Europe + NeoNephos 联合发布, 2026-10-07
  • 样本：367 家欧洲组织调查 + 访谈

关键数据：

  • 94% 欧洲组织认为 digital sovereignty 重要（61% 认为「非常重要」）
  • 76% 组织报告 AI 工具帮助他们从开源中获得更多价值
  • 31% 组织仍没有正式开源治理框架
  • 48% 维护私有 fork（平均每个 fork 每个 release 周期要维护 311 小时、维护 9.5 个 fork；28% 说不清花了多少钱）
  • 有成熟治理的组织开源 ROI 4.6×，无治理的 3.6×

「开源之道」点评（Williamson L2 制度环境层的量化证据）：

  • 这是 diginomica 2026-10-08「Who owns the stack?」命题的量化支撑——贡献被度量，但贡献的治理权重没有被度量。这是「度量权」命题的最强量化证据：94% 认为重要（贡献/参与被度量）vs 31% 无治理框架 + 48% 维护私有 fork（治理权未制度化）。
  • 交易成本的实证：31% 无治理框架 + 48% 维护私有 fork + 无法追踪 fork 成本（28% 说不清花了多少钱）= Williamson L3 治理机制层的交易成本被调查数据化。
  • 与 10-12 LF Europe GM Carrez 表态构成因果链——10-12 Carrez 说「欧洲要技术主权 ≠ 开源能自动产生欧洲主权」，本次数据给出了具体证据：贡献比例（40%）和治理权（未量化）之间的差距本身就是「治理权断层」的实证。
  • 与 Tokenomics Foundation 472 家数据集构成方法论对照——两个都是 LF 旗下大样本调查，一个覆盖全球 AI 经济（472 家、$4.6T），一个覆盖欧洲开源（367 家）。两个数据合起来描绘「LF 作为度量权输出方」的完整能力。

未来检验点：

  • ①欧洲是否会在 2027 年前设立类似 Tokenomics Foundation / x402 Foundation 的主权基础设施（不只是「参与」，而是「设立」）——这是 Carrez 命题的直接回应；
  • ②31% 无治理框架的组织是否有具体名单——判断是「欧洲整体治理缺口」还是「企业规模差异导致」；
  • ③是否有第三方机构（如 EU、CISA 或 ETSI）跟进做独立调查验证——LF 自有调查存在自我宣传偏差。

误判风险：94%「认为 digital sovereignty 重要」是自我选择样本（参与调查的组织本来就有开源兴趣），不能外推到整个欧洲企业。LF 自有调查的自我宣传偏差需要外部数据交叉验证——与 Tokenomics Foundation 472 家数据的偏差风险相同。

六、合规层：SBOM 从「倡议」到「框架版本 1.0」#

🏭 OpenChain Automotive SBOM Framework 1.0（2026-10-07）#

  • 目标："汽车行业软件的更大可靠性与可追溯性"

「开源之道」点评（「合规作为开源基础设施」命题的第二个行业实例）：

  • ③SBOM 1.0 是否与 EU CRA（Cyber Resilience Act）形成互补——EU CRA 是政策强制，SBOM 1.0 是行业标准，两者是否有对齐。

误判风险：SBOM 1.0 的实际落地情况需要汽车厂商采购政策验证——「框架 1.0 发布」不等于「实际采用」。作为「合规作为开源基础设施」的第二个行业实例保留。
