2026-11-06 「开源之道」·深度：同一周里，「拒绝」被丢在了三个开缝的地方#

这一篇不是论文，是三份材料的对读#

今天是「类型：分析」，不是荐书也不是论文略读。封面用的是自制材料卡，不是书籍 SVG 卡，也不是文生图。

理由写在前面：素材库里 11-03 至 11-05 三天积了六篇全文深审（Django 组织法、MCP 破坏性工具审批、curl 撤赏、量子开源核验、Foresight-SWE、BOBA），四篇仍在冰箱里（11-04/11-05 入库，未满 1 天冷却期），最新的 #242 还是今天入库。硬按节奏把一篇未读透的东西推出来，不如把已经读透的三份放在一起看。

而它们放在一起之后，出现了一个我只在单篇里看到一半的东西。

三份材料，各缺一个位置#

材料一｜Django 组织法（2026-11-03 一手拉取，django/django@main，组织法 297 行逐条对读 + 137 个 PR body 解析）

这份宪法罕见地厚：合并者下限 3 人、禁自合且列了四项豁免、合并者与指导委员会互斥、委员会可否决、可下令回滚、还可以拒绝表态。DSF 全资 Fellow 经费条款与 Releasers 一节逐字同款——说明它是模板化条款，不是为合并者量身定做。

我当时的判据是：看一个项目里「拒绝」这个动作有没有名字。Django 有四个名字。

但今天回看，这条判据还差半步：有名字，不等于有记录。 那四项豁免——另一合并者、指导委员、triage&review、安全团队——在 GitHub 的 approvals 里没有任何可区分的标记。merged_by 只记谁按了那个绿按钮，不记依据谁的批准。于是「禁自合」这条最硬的规则，在执行层留下的痕迹是一句四选一的自由文本。

材料二｜MCP 破坏性工具审批（#235，arXiv 2611.02527；41 宿主 / 1,995 标记 / 366 工具抽样）

  • 服务端侧：补回提取器漏掉的 83% 破坏性工具后，90%（95% CI 82–95）的破坏性工具没有任何服务端确认。
  • 宿主侧：41 个宿主里 32 个默认无审批，其中 16 个 SDK 全部如此。
  • 组合起来：60.7%（应用）/ 74.9%（全宿主）不存在任何强制性的「人来批一下」。
  • 反向实验最能说明问题：「未标注只读即弹窗」一步能把组合份额压到 5.4%——换来 82.6% 的误伤率。全 fail-closed 则 79.4% 的正当操作被拒，其中 14.4% 已经拿到人工批准，仍被拒。

最后那个数字是全篇的题眼：批准没有被记下来。 用户点过一次「允许」，但这个「允许」在服务端不存在。于是每一方都在自证清白，而中间那句「人已经批过了」没有人负责传递。

材料三｜curl 终止漏洞赏金（#236，docs/BUG-BOUNTY.md + vuln.pm 149 条 CVE 全量复算）

  • 赏金的真实终点是 2025-12-28；2026 年公布 65 个 CVE，62 个奖金为 0，年度奖金总额 US$1,515，六年来最低。
  • 但报告没停：2026-10-14 一次公布 24 个 CVE，全部来自 2026-09-03~09-18 两周内提交的报告。
  • 规则写得极清楚：bug_report.yml 顶部必读段逐字要求「用你自己的、人能读的声音」写报告；BUG-BOUNTY.md 写着不发奖金的原因是「奖金给了人们太强的动机去查找和编造『问题』」。
  • 而整树 4,602 个文件、16 个工作流、25 个脚本里，没有任何一个 AI 痕迹检查器；reproducer 字段是 required: false。

规则全部写在人读的提示里，没有一条落在机器能拒绝的位置上。curl 的解是把判断成本整体交给维护者——博客原话是这些无穷无尽的粗制投稿「serious mental toll to manage」。

三张处方，一次都没做到「不能被绕过」#

  • Django｜想禁止：自合、不披露 AI 参与｜判断依据：作者自证勾选 + 四人互看｜能不能绕过：能——表单允许双空，豁免在平台层无标记
  • MCP｜想禁止：agent 未经人批准执行破坏性操作｜判断依据：工具标注 destructiveHint + 宿主 if 语句｜能不能绕过：能——标注在 39/41 宿主上改了等于没改，默认无审批
  • curl｜想禁止：无意义的 AI 生成投稿｜判断依据：人读的提示文本 + 维护者逐条判断｜能不能绕过：能——没有检查器，没有必填复现步骤

三种成本结构完全不同的公地——一个有基金会和宪章（Django）、一个连规范都没写全（MCP）、一个由 BDFL 一人扛（curl）——在同一周里收敛到了同一种解法：把规则写给人，指望人自愿遵守。

这不是巧合，也不是「作者偷懒」。它是一个稳定的均衡：写成机器可拒绝，需要在规则和检查器之间接线；而接线的活儿没有任何人被指派去做，也没有任何账目记着它。

Williamson 的三变量，在这里一次全中#

用交易成本理论看这三处，资产的三个属性指向同一个答案——

  • 不确定性极高（AI 生成的贡献、agent 调用的意图，季度级重建）；
  • 资产专用性接近零（模型能换、宿主能换、投稿者能换）；
  • 交易频率极高（每个 PR、每次工具调用、每一份报告）。

按 Williamson 的逻辑，这个组合本该被内部化：交给一个有名字、有责任能力、能被追到的层级去裁决。而开源做的是相反的动作——它把裁决外部化成了一种公共品：谁来都能说，谁说了都不留痕。

于是「审查」变成了一件没有主的事。

奥斯特罗姆：不是治理不善的公地，是还没被承认为公地的公共品#

我原以为这三处是 Ostrom 八原则的失效。对读完三份材料，这个说法太重也太轻。

太重，因为八原则预设的是一个已经在运行的治理体系；而这三处的共同点不是「监督弱」，是监控这一环根本没有落在任何人头上。MCP 的批准确认、Django 的豁免标记、curl 的投稿筛选，都是「规则写了，但没有人被指派去读它」。

太轻，因为一旦把它们当成「公地」，就会问错问题——公地治理的经典追问是「成员之间怎么互相监督」；而这里的问题是「这个公地有没有一本能被外部核查的账」。这是前一个问题。

所以更准确的说法是：这是一批还没有被承认为公地的公共品。 参与是开放的、使用是免费的、维护是自愿的——但它缺的不是成员间的规则，是一个记账的人。

「拒绝的权利」可以再拆一格#

我在 curl 那篇里写过一条桥接概念：公地维护者最不可再生的资源不是注意力，是拒绝任何东西的许可。三份材料对读之后，我想把它拆成两格——

  • 拆一：拒绝的许可（permission to refuse）——一个人或者一个角色，被规则授权说「不行」。Django 有四个具名位置，curl 有一个（应当说：在 BDFL 一人身上），MCP 里一处都没有。
  • 拆二：拒绝的落点（where refusal lands）——说「不行」之后，这句话被记在哪里，以及下一次别人凭什么知道它被说过。

拆开之后，三种情况的差别立刻变得可测量：

  • Django：有许可，落点靠人。 四个位置都在，但落点是一次性的、外部的、无人付费的核查——我自己做这次核查的代价是拉 50 个 PR 的元数据、被限流一次、手写模板正则。这个成本比写那部宪法还高，且没有任何岗位为它付钱。
  • curl：有许可，落点是零。 拒绝发生在维护者的脑子里；vuln.pm 是公布台账不是申报台账——被拒绝的投稿永远不会出现在里面。你无法从任何公开数据回答「撤掉奖金后投稿少了几成」。
  • MCP：许可分散在 41 个 if 里，落点是负的。 用户点了允许，服务端不知道；14.4% 已批准的操作被 fail-closed 再拒一次。这儿不只是没记住，是把已经发生的许可判为无效。

三档不是程度差别，是三种不同的制度状态。而它们的共同后果是同一个：「谁说过不行」这件事，在生态层面不可回答。

对「开源之道」的三条自省#

写到这里，我得先说一句不好听的话。

一、我自己的判据也只量了「有没有名字」，没量「有没有落点」。 11-03 那天我给出的判据是「看拒绝有没有被安放在一个不依赖某个具体人的位置」。这句话是对的，但它默认了「安放 = 写在文本里」。三份材料证明，写在文本里的拒绝，和能被第三方核查的拒绝，是两件事。判据需要加后半句：说不行之后，谁能在不问你本人的情况下看到它。

二、用「规则是否可执行」量行政式开源，这把尺子本身也来自某一支传统。 Williamson 的内化逻辑、Ostrom 的八原则、甚至「可核查性」这个价值，都是特定制度史的产物。今天这三处——一家基金会代管的美国项目、一批美国厂商的产品默认值、一个瑞典 BDFL 的个人决策——全都达不到这把尺子的刻度。如果连它们都达不到，那这把尺子就不是用来给「中国 vs 西方」定性的，是用来给自己定位的。 这一点得诚实。

三、「生态是结果不是手段」在这里有个反向证据。 若生态真是自发不可规划的，那这三处开缝就该随规模自愈；但三处都是规模上去之后才出现的——Django 的合并者多到要写禁自合，MCP 宿主多到 41 个默认值各写各的，curl 的投稿多到需要撤奖金。开缝是规模的结果，不是规模的原因。 自发的部分在于「谁来做这件事」不可规划；该做的这件事本身，是可以被指定、被接线、被记账的。

一句话判断#

规则写得越清楚，越容易让人忘记它还需要一个不被当事人控制的落点。「拒绝」的第一格是许可，第二格是落点——三份材料里，只有第一格被认真写过。

延伸思考#

  1. 「落点」能不能被标准化？ MCP 的反事实实验给出了一个便宜的答案：要求一个「已批准」的回执。这不需要更强的模型，只需要规范里多一个字段，宿主多传一次。为什么没有？因为规范由厂商写，而厂商的默认值是资产不是制度。
  2. Django 的落点该长什么样？ 最便宜的做法不是加勾选框，是让「谁批准了」变成 PR 上的一个结构化字段，而不是 approvals 列表里的自由文本。这样四项豁免才有可查的痕迹——而平台本身不做这件事，所以任何项目都只能在自己的模板里补。
  3. curl 的选择是否更诚实？ 它至少没有假装有落点。撤销奖金、保留人工判断，这是一次把落点明确归零的动作，代价是维护者的精神健康。反过来问：一项必须靠人的健康来维持落点的制度，还能叫制度吗？
