2026-11-10 「开源之道」·论文略读：一份可复算的复制包里，有三处它自己撑不住的结论#

论文信息#

字段内容
标题Divergence or Convergence? A Deep Insight into the Crowd Collaboration and its Productivity in Open Source Software based on Entropy
作者Yang Shen、Tao Wang（通讯）、Xunhui Zhang、Yang Zhang、Cheng Yang、Bo Ding、Huaimin Wang（国防科技大学 · 复杂关键软件环境全国重点实验室）
发表CHI ‘26（2026-04-13~17，巴塞罗那），1585:1–1585:17，17 页，CC BY 4.0
DOI10.1145/3772318.3791405
基金NSFC No.62332005（单一基金，无企业资助）
复制包github.com/anonymous2026CHI/2026CHI-replication-package（3 份 R 脚本 + 4 份 xlsx + additional_validation.zip 4.6 MB），2025-12-05 最后更新
样本8 个 GitHub 项目 × 月面板：docusaurus、playwright、nacos、googletest（公司驱动）+ fastapi、vue、rustdesk、ohmyzsh（社区驱动）；12,720 forks、39,300,748 commits；面板 N=732（RQ1）/ 739（RQ2）/ 739（RQ3）

一句话推荐#

它把「谁的努力被按比例看见了」第一次写成了一个可算的量，并且把复制包真的公开了——我用 Python 把主表逐条重跑，数值对齐到小数点后两位。然后我做了论文自己没做的那件事：剔一个项目。两条被摘要当作核心发现的结论，在它自己的数据里各自翻了符号。

内容概要#

指标定义（第 3.2 节）：

$$H_{conv} = \bigl(1 - \mathrm{JSD}(P_o \,\|\, P_m)\bigr)\times \frac{C_m}{C_o}$$

$P_o$ 是窗口内各 fork 的原始 commit 占比分布，$P_m$ 是同一窗口内各 fork 的被合并 commit 占比分布，$C_m/C_o$ 是总合并率。作者的解释很直白：$1-\mathrm{JSD}$ 度量「分散的创新被按比例吸收」的程度，$C_m/C_o$ 度量吸收的绝对效率，两者相乘得到「融合效果」。

这个设计有真东西。 它比 merged PRs / closed PRs 之类静态比率多了一个维度——分布的形状。如果原始提交均匀分布在 100 个 fork 里，而合并只来自 1 个 fork，$1-\mathrm{JSD}$ 会很低；如果两边同形，即使量小也高。「谁的努力被按比例看见了」第一次变成了一个可算的量。

三个研究问题：RQ1 融合熵 ↔ 新缺陷数（Performance）；RQ2 ↔ 新 commit 数（Activity）；RQ3 ↔ issue 平均解决时长（Efficiency & flow）。三维取自 SPACE 框架（Forsgren 等 2021）。

核心 / 外部的判定（3.3 节，全篇最扎实的技术细节）：作者把 GitHub 的 53 类 issue 级事件逐一手工标注权限要求，发现其中 16 类外部贡献者可无特权执行，其余 37 类需要管理权限。执行过需权限事件的账号标记为 core team，其余为 external。这比「查 collaborator 名单」或「只看 write 权限」都细——特别是它救回了 GitHub 上 Triage 角色这类有治理权但无写权限的人。

复算：主表对得上，两条方向性结论对不上#

复算流程严格照抄 panel_regression_for_RQ1.R：complete.cases → log(x+1) → scale() 全标准化 → 全交互项，用 statsmodels.MixedLM 随机截距替代 plm(random.method="amemiya")。

  • RQ1 新缺陷：非公司 β=−12.25（原文 −12.36）、公司 −14.51（−14.51）、全样本 −13.21（−13.22）——三组全部对齐
  • RQ2 新 commit：非公司 +199.16（+198.26）、公司 −35.84（−39.97）、全样本 +13.55（+13.60）——对齐
  • RQ3 解决时长：非公司 +86.72（+86.73）、公司 −28.94（−30.05）、全样本 −18.13（−18.14）——对齐到小数点后两位

论文没有算错。后面两道坎都不在算术上。

第一坎：ohmyzsh 的融合熵在 176 个月里恒等于 0。 我把它拆开看：ohmyzsh 176/176 个月（100%）融合熵 < 0.01（最小 1.19e−5，最大 0.0091，中位 0.0064），连续 176 个月无一反弹。对照 docusaurus 中位 0.860、nacos 0.661、playwright 0.568、fastapi 0.528、rustdesk 0.357、googletest 0.219、vue 0.156。

机制不难推：ohmyzsh 的 4,528 个 fork 里绝大多数是「装了就改自己配置、从不回传」，这个 fork 结构决定了它的融合熵结构性贴地。这不是一个低值，这是一个没有变异的变量。 标准化之后它变成一列常数，在回归里只增加噪声、不提供识别。

剔除它之后：RQ2 非公司子样本 β 从 +199.16（p<0.0001）翻为 −114.00，95%CI[−275.92, +47.93]，p=0.168，不显著且符号翻转。 论文「社区项目融合熵升高带来更多 commit」这条正面结论，由 ohmyzsh 一个项目的常数项撑着。（RQ1 非公司剔除后 β=−12.31，p=0.025，照样显著，稳健。）

第二坎：公司子样本只有 4 个项目，留一法下结论各自翻一次。

RQ1 公司子样本（β=−14.50，p=0.010）：剔 playwright → +8.05（p=0.002）；剔 googletest → +54.50（p=0.004）。两次都是「剔一个项目 → 系数翻、仍然显著」，不是变弱，是变成相反方向的显著。

RQ2 公司子样本（β=−35.84，p=0.007）：剔 docusaurus → −57.78（p=0.057）；剔 nacos → −27.81（p=0.057）；剔 googletest → −12.49（p=0.750），塌掉。

你以为在估计一个效应，其实在估计「哪一个项目被算进去了」。 而全样本 RQ2 主效应本来就已经 p=0.316 不显著——论文对这一点的汇报是诚实的（“lacks a significant main effect”）。诚实的报告方式，反而让读者更容易忽略：一个全样本不显著的变量，被拆成两半之后各自显著且方向相反，这个拆分本身就该被质疑。

为什么值得读#

因为它是目前极少数「敢让人核对」的开源实证论文。 复制包、三份 R 脚本、审稿回应全都公开，主系数在 Python 近似下逐条对齐。这在今天属于少数派。按本 wiki 此前的判据（可复算性作为治理判据），它是一篇可被怀疑的论文——它给足了让人核对的材料，所以我核对出了它的边界。这不是揭短，是把它的结论裁到它撑得住的那块地。

因为它提供了三样值得留下来的东西。

① 「按比例吸收」作为可计算量，本身是进步。 现有 fork 研究最常引用的是静态比率（contributing forks / active forks、merged / closed PRs、hard fork 是否存在），这些指标都没有时间维度。融合熵是窗口化的，可以画时间序列、可以做面板、可以接预警。这是真实的方法增量，与它有没有估对效应无关。

② core/external 的权限事件标注法（53 类 → 37 类需权限）是可复用的基础设施。 它应该被「agent vs human」那类研究借用——因为「谁是核心」在任何 AI 贡献研究里都是分母问题，而本文给出了比 collaborator 名单更细的一层。

③ 「熵」这条线的谱系已经成形。 同一团队三年三步：issue entropy（PACMSE 9(7), 2025-10, DOI 10.1145/3757399，与新增缺陷强正相关、commit 关系取决于公司赞助）→ convergence entropy（本文，与缺陷负相关、commit 与时长方向随公司/社区变）→ 动态 issue-PR 熵含 agent 维度（PACMSE 3(ISSTA), 2026-10, DOI 10.1145/3832206，83 仓库，涉 agent 的协作与新缺陷负相关）。

注意这个转折：两个都叫「熵」、同一组人提出、同一套 SPACE 框架，对缺陷的方向却相反。 不是矛盾——前者度量「事件序列有多乱」，后者度量「吸收有多成比例」。但它暴露了一个真实的传播风险：「熵」这个词在转述中会被当成同一个概念，「熵高=好」或「熵高=坏」会随引用链漂移。

为什么对开源社区如此重要？#

一、可复算 ≠ 结论成立，这是两个不同的门#

此前记下的正面样本是「可复算 → 结论更可靠」。本文是第一个「可复算但结论不成立」的样本：它能保证「我能重算出你的数字」，不能保证「你的数字支撑你的话」。

于是判据要升一级：

$$\text{存在性} \;<\; \text{完整性} \;<\; \text{可复算性} \;<\; \textbf{稳健性}$$

「稳健性」是本文补上的第四级——换一个子样本、剔一个项目，结论还在不在。 这个动作成本极低（一行代码），却能一次性筛掉大量看起来很硬的实证结论。

二、一个 2.5/8 的指标进仪表盘，挤掉的是那 5.5 条#

作者在 3.2 节解释指标性质时写下这句话：

“close alignment suggests a meritocratic system where diverse innovations are proportionally recognized and incorporated.”

这句话把「分布同形」直接读成了「功绩制」。 但两者不是一回事：分布同形（$P_o \approx P_m$）度量的是「各 fork 被吸收的比例与其产出的比例一致」——它是一个会计口径的一致性。功绩制度量的是「贡献按质量被承认」——它是一个判准。

一个项目可以同时做到：分布高度同形，且绝大多数合并仍来自同一批人（因为产出本来就集中在那批人身上）；也可以做到分布严重不同形，但每一次合并都经过了更严格的评审。前者会被这个指标判为「功绩制良好」，后者会被判为「有偏见」。指标无法区分这两者，因为它没有「质量」这一维。

用奥斯特罗姆八原则对照，这套指标覆盖了哪几条：

Ostrom 原则指标是否触及说明
①清晰边界部分core/external 的判定是本文最扎实的技术贡献（53 类事件 → 37 类需权限）
②规则与本地条件相符否指标不读规则文本
③集体选择安排否谁能改规则，完全在模型之外
④监督间接$1-\mathrm{JSD}$ 可视为「吸收过程可被测量」，但不含「谁在监督」
⑤分级制裁否无
⑥冲突解决否无——被低比例吸收的 fork 没有申诉通道
⑦对组织权的最低认可否无
⑧嵌套治理否无

八条里触及两条半。 这不是缺陷——一个指标本来就不该覆盖制度全貌。真正的风险在于：论文 6.3 节明确提出要做 “project dashboards”，当这种指标进入仪表盘、进入「项目健康度」评分、进入基金会年度报告，被测量的那两条半就会挤掉没被测量的那五条半。度量权的上游一旦确立，下游的治理讨论就会被重新组织在它的坐标系里。

三、同一个指标，在两种组织形态上测的是两个东西#

本文有一个作者没点出的发现：8 个项目里融合熵分布跨了整整两个数量级（ohmyzsh 中位 0.006 到 docusaurus 中位 0.860）。作者把它当噪声，我倾向当作信号：它测的可能不是「融合效率」，而是「项目的分工形态」。

ohmyzsh 是「每人各改自己配置」的模板仓库，docusaurus 是「统一文档站」的协作仓库——两者的 fork 结构差异是治理形态的差异，不是效率的差异。 同一个指标在「俱乐部」和「产业设施」两种形态上测量的是不同的东西，而指标不知道自己是哪一种。

延伸思考#

一、四条可以带走的方法判据#

  1. 常数即缺失（a constant is a missing variable）——当某个自变量在一个子样本的整个时间跨度上恒等于某个值，它在这个子样本里不再是变量，而是缺失。它不会让回归报错，只会让系数由剩下的少数项目决定。判据：做任何子样本回归前，先打印每个自变量在每个组内的最小/中位/最大值——分布跨两个数量级就是警报。
  2. 机构层特征在 4 个机构上不可识别——「公司 vs 社区」是一个机构层二分，用它去切一个只有 4+4 个机构的面板，等于用 4 个观测估计一个机构层效应。这类设计的正确自由度从来不在 N=732 里，而在组数=8 里。 这是少组长面板的伪重复，与「18 个观测撑 919 行回归」的生态学谬误是同一个错误的两种外观。
  3. 度量覆盖度（metric coverage）——指标覆盖的制度维度数 / 制度维度总数。融合熵对 Ostrom 的覆盖是 2.5/8。判据：任何「项目健康度」类指标，都应公布它覆盖了 Ostrom 的哪几条、明确弃权了哪几条。
  4. 熵的方向漂移——同名的「熵」在引用链上会脱离原定义。引用任何「熵」指标时必须带上定义与方向；不带方向的相关性是伪引用。

二、4 个组做随机效应面板，为什么 plm 不报错#

4.3 节写做了时间固定效应检验、pFtest、Hausman 检验、异方差检验、偏度检验。但 Hausman 检验在固定效应与随机效应的估计差上构造统计量，随机效应模型又用 Amemiya 方法估方差分量——4 个组时，方差分量的估计几乎没有自由度可用，检验的渐近性质无从谈起。

这不是指责作者不用心——plm 是这个领域的事实标准。问题在于领域标准本身没有为「少组长面板」设一道闸。指标是可复算的，但指标之上的推断，其可靠性依赖调用者是否理解面板渐近的方向。

三、标准化系数被当成了效应量#

表 2 的 −12.36 意为「融合熵每上升一个标准差，新缺陷减少 12.36 个/月」。但融合熵全样本实测标准差是 0.321（中位 0.345，取值域 0~1）——一个标准差的变化，是这个变量取值范围的三分之一。表 4 的 +86.72 同理：融合熵上升一个标准差，issue 平均解决时长增加约 87 天。这个量级在任何工程语境里都不成立，说明模型在标准化尺度上做的是体外推：它告诉你方向的统计显著性，不告诉你任何可行动的幅度。而 RQ3 整组 R² 只有 0.265 / 0.183（论文自陈 “moderate”），80% 以上的变异不在模型里，符号可以有，效应量谈不上。

四、最干净的下一个本土缺口：这把尺子量不到#

8 个项目全部是 GitHub 上 star 前 1,000 的西方平台仓库，无一例来自 AtomGit / Gitee / OpenAtom / ModelScope。所以本文只能提供「开源融合过程如何被度量」的基线，不能提供任何制度环境的对照。

而它恰恰提供了一个现成的本土研究缺口：融合熵在中国平台上的取值分布是什么？ 如果本土平台的 fork → PR → 合并链条根本不以 fork 为起点（ModelScope 的分发已经绕过 fork 模型），那么这个指标在中国语境里可能连定义域都没有——这不是「中国分数低」，是**「尺子量不到」**。这是我目前能看到的最干净的、方法上无争议的下一步。

金句#

可复算只保证「我能重算出你的数字」，不保证「你的数字支撑你的话」。

你以为在估计一个效应，其实在估计「哪一个项目被算进去了」。

一个 2.5/8 的指标进了仪表盘，它挤掉的是那 5.5 条没被测量的。

关键限制（当「方法扎实、复制包公开、但推断部分需自己复核」的论文读）：

① 无 R 环境，plm(random.method="amemiya") 用 Python statsmodels.MixedLM 随机截距近似——主系数精确对齐（差 <0.1），但 R²/SE/p 不逐位一致，翻符号/失稳结论按方向与显著性判读，不按精确数值引用；② RQ3 剔除检验在 Python 下模型奇异（3 个项目组），因此「RQ3 是否稳健」判为未决，不是判为不稳健；③ 只复算主效应，63 个交互项未覆盖；④ 复制包只给已算好的 convergence_entropy 列，不含 fork/commit 原始事件（12,720 forks / 3,930 万 commits 的采集脚本未附）→ 数据可复算，指标不可复算，这是复制包的真空位；⑤ 8 项目的公司/社区二分按 Spinellis 等 2020 启发式，未复核，且该二分在中国语境本身需重写；⑥ 8 项目全为 GitHub 西方平台仓库，中国平台零样本——只能提供基线不能提供对照；⑦ 作者对「相关非因果」的声明清楚（“conjectures”/“speculative”），本次批评限定在效应量与可解释性，不是指控作者隐瞒因果；⑧ 读的是 CC BY 4.0 正式出版版（作者站点 zhangxunhui.github.io/files/CHI_2026_sy.pdf 与 ACM DL 同源），不存在「未同行评审」问题；⑨ 一个视角，不是定论。
